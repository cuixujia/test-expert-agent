# PRD 编写约束要求

> **给谁看**：需求撰写人（产品/业务），在 PRD 交稿前使用。
> **解决什么**：测试流程会逐字引用你的 PRD 原文来生成测试点和测试用例。原文写得清楚、带编号、能摘抄，测试一次就能过；写得不清楚，质检会打回来请你澄清，多耗两轮流程。**本文只讲怎么写能一次过，不替代质检本身。**
> **粒度定位**：这份 PRD **只写一个业务功能**。测试工作空间按业务功能编号建目录、一次只处理一个功能；写成整系统、全项目的大需求，超范围的内容不会被使用，反而会稀释焦点、干扰测试定位。

## 你的 PRD 会被这样使用

```mermaid
flowchart LR
    A["PRD 交稿"] --> B["生成只读快照"]
    B --> C["按编号建锚点（原文定位标记）"]
    C --> D["从原文提取测试点"]
    D --> E["派生测试用例"]
```

链条上每一步都直接引用你的原文，没有任何一步靠猜——所以「写得清楚、带编号、可摘抄」就是你最大的加分项。

## 前提：一份 PRD ＝ 一个业务功能

- **对号入座**：一个业务功能（如「定期存款购买」）在平台有唯一编号，测试工作空间按它建目录。所以 PRD 的覆盖范围 = 这一个业务功能。
- **文档内不再拆层级**：六要素（业务流程/业务规则/业务对象/业务界面/完成标准/存量功能关联）直接描述这个业务功能本身，**写一份，不往下拆成若干功能点**。
- **手头是大需求怎么办**：先把本功能相关内容裁剪成单独一份 PRD 再交稿；父级需求（BRD 等）只引用需求 ID，不整篇搬运。
- **不要写大而全**：属于其他业务功能的内容测试不会读取；引用其他业务功能时按黄金规则 10 写明编号或文档名；其他系统只登记依赖和协作边界，不展开设计。

## 三步写完一份合格的 PRD

### 第一步：按 7 章搭骨架（照抄即可）

| 章 | 写什么 | 必需 |
|---|---|---|
| 1 文档元信息 | 需求 ID、业务功能名称与平台编号、负责人、版本、日期 | ✅ |
| 2 背景与依据 | 为什么做、依据哪份文档（父级需求只引 ID，不整篇搬运） | ✅ |
| 3 目标与范围 | **一句话定边界：本 PRD 只覆盖业务功能〈名称＋平台编号〉**；纳入范围写客群/产品/渠道，**排除项单列** | ✅ |
| 4 业务流程 | 参与角色；主流程步骤；**异常事件逐个列**（触发条件 → 处理动作 → 结果方向） | ✅ |
| 5 业务功能 | 对这一个业务功能写六要素（第二步模板）——**全文核心，只写一份** | ✅ 核心 |
| 6 非功能约束 | 性能/安全/可用性；有数值给数值和验证方式，没把握的写「待确认」 | 涉及时 |
| 7 待澄清事项 | 自己没把握的点集中列一处 | 建议 |

> 示范 PRD《定期存款购买》可作内容参照（其规则边界、流程事件取材于它）；注意它内部用 F01~F11 拆分组织，按本文口径应收拢为一份六要素，不再往下拆。

### 第二步：六要素直接写业务功能本身

填空模板（复制后把尖括号换成自己的内容）：

```markdown
## 业务功能：<业务功能名称>（<平台编号>）

### 业务流程
- 主流程：<谁 → 从哪进入 → 按什么顺序做什么 → 得到什么>
- 分支：<条件A → 处理A>；<条件B → 处理B>
- 异常：<异常情形 → 拦截动作 → 提示/引导什么>

### 业务规则
- <规则1，给数值或公式>
- <规则2>

### 业务对象
- <对象名>：<字段1、字段2、字段3…>

### 业务界面
<有界面：谁用、在哪个页面、关键操作与入口>
<没界面：本功能为后端接口功能，无直接业务界面>

### 完成标准
- <结果方向>（<怎么验证>）

### 涉及存量功能编码清单
<无；或 已有存量编号 / 依赖某系统>
```

写成什么样算好——以示范 PRD 同名业务收拢为一份六要素的成品为例（有界面功能的写法）：

```markdown
## 业务功能：定期存款购买（DQDKGM）

### 业务流程
- 主流程：客户登录网银 → 浏览产品货架 → 选定产品 → 选付款账户、录入金额、
  选到期处理方式 → 实时试算到期利息 → 勾选确认风险提示 → 提交（资格校验、
  余额与限额校验）→ 核心系统开立定期账户并划转资金 → 展示交易结果
  → 发送通知、触发营销活动
- 分支：产品售罄 → 显示售罄状态并推荐同类在售产品；经推荐链接进入 → 自动关联推荐人
- 异常：
  - 余额不足 → 拦截提交，提示缺口金额 = 购买金额 − 可用余额
  - 证件过期 → 拦截提交，提示先更新证件后方可办理
  - 系统超时 → 提示「处理中，请稍后查询」，后台核实后通知结果，不引导重复提交

### 业务规则
- 起存金额、递增单位按产品定义，不满足即拒绝并提示
- 限额：不超单户持有上限、当日累计限额；II 类户另受日累计 1 万、年累计 20 万约束
- 执行利率按购买时点公示利率锁定，存续期内不受利率调整影响
- 起息日为购买当天；到期日 = 起息日 + 存期
- 到期处理方式（不转存 / 自动转存）购买时选定，到期前可变更

### 业务对象
- 定期存款产品：产品代码、名称、存期、年利率、起存金额、剩余额度、状态
- 存款合约：存款账号、本金、执行利率、起息日、到期日、到期处理方式
- 交易流水：流水号、交易时间、金额、渠道、推荐人、交易结果

### 业务界面
个人网银存款频道：产品列表页（筛选排序）、产品详情页（利率说明、提前支取规则）、
购买录入页（试算展示、风险确认勾选）、结果展示页；入口为产品列表/详情页的「购买」按钮

### 完成标准
- 校验全部通过时完成开户与资金划转，账务借贷平衡
- 合约利率锁定，事后不可变更；关键信息确认留痕
- 试算展示的到期利息与实际成交一致（功能走查核对）
- 校验接口响应时间 ≤ 500ms（压测验证）

### 涉及存量功能编码清单
- 渠道侧已有存量功能：定期存款购买 FUN202608192089893037232488449（本文维护其核心系统侧新增能力）
- 依赖：SYS_RATE 利率管理系统提供利率参数；客户信息系统提供证件状态与风险等级
```

**写作顺序**：先第 3 章定范围（含排除项）→ 第 4 章流程与异常事件 → 第 5 章写一份六要素 → 第 6 章非功能 → 第 7 章待澄清。

### 第三步：交稿前三遍查

1. **搜词查打架**：搜「权限/校验/状态/触发/入口」——同一件事在两处说法不同立即改成一致（这是质检打回的头号原因）
2. **数八样**：对照整份 PRD 核对 目标、范围、角色、前置条件、结果方向、分支、排除、依赖 都找得到
3. **过清单**：把文末「交稿自检清单」逐条打勾

**一句话判定写没写够**：交给一个没参与讨论的测试同事，他只看原文、不问你，就能说出这个业务功能要验证什么、怎么算通过——做不到，就是没写够。

## 十条黄金规则

| # | 规则 | 一行说明 |
|---|---|---|
| 1 | 用 md 或 txt 交稿 | md/txt 直接生成快照；docx 可自动转文本；PDF、扫描件、纯截图会让文字核对失效，测试质量直接打折 |
| 2 | 引号统一用直引号 | 全文用 " 和 '，不用弯引号（“ ”），核对摘录时不会差一个字符 |
| 3 | 交稿即冻结 | 流程开始后 PRD 不再修改，发现问题走「澄清登记」（你的说明被编号登记下来，不改原件）；所以定稿前务必过一遍文末清单 |
| 4 | 章节和条目带稳定编号 | 章节编号、流程事件、规则条目都编上号——原文编号会直接用作测试依据的定位标记 |
| 5 | 业务功能名称全文统一 | 测试点名称直接抄 PRD 原词，业务功能名称是全文唯一的主键，逐字一致、不换叫法 |
| 6 | 流程图必须配文字版步骤 | 图可以保留作参考，但判定依据以文字为准——图里的信息正文要有等价描述 |
| 7 | 规则给到数值、公式、枚举 | 如「II 类户日累计 1 万、年累计 20 万」「到期利息 = 本金 × 年利率 × 存期（年）」；确实定不了的写「待 XX 阶段确认」并给个大致验证方向 |
| 8 | 排除项单独列 | 「外币定期存款不在本次范围」写明之后，测试才不会越界设计 |
| 9 | 界面有无显式声明 | 有界面写清页面与入口；纯后端功能写「本功能为后端接口功能，无直接业务界面」，测试据此决定要不要前端资料 |
| 10 | 引用其他业务功能写明编号 | 写「定期存款支取见〈功能编号/文档名〉」，不写「见前文相关功能」；其他系统只登记依赖和协作边界 |

## 全文自检：五个维度

| 质检查什么 | 你要写成什么样 |
|---|---|
| 完整性：目标、范围、角色、前置条件、结果方向、主要分支、排除项、外部依赖 | 每项业务能力都能找齐这八样，缺一样测试就只能推测或停下来问你 |
| 一致性：同一规则全文只说一套 | 两处描述不同＝最高优先级问题，必被打回；写完回头搜关键词核一遍 |
| 无二义性：一句话只有一种读法 | 不用「等」「视情况」「原则上」；两可时写明以哪个为准 |
| 可测试性：执行后看得见分对错 | 每条能力都答得上「执行后看什么结果定过/不过」；答不上来的先别写，或标「待澄清」 |
| 可追溯性：每项能力定位到原文 | 靠编号和名称统一做到；引入外部文档时在正文写明出处 |

**最容易打架的七处**（真实质检的高发区，每处全文只说一套）：

> 权限与可见范围 · 按钮/操作入口归属 · 状态枚举与流转 · 角色与能力分配 · 字段取值与统计口径 · 触发时机与时间标准 · 校验时机（何时校验、校验什么、不过怎么办——多处各说半句拼不成完整链，是已真实发生过的踩坑）

## 交稿自检清单

- [ ] **范围收敛：全文只覆盖一个业务功能**，文档内不再做功能拆分，六要素只写这一份
- [ ] 文档是 md/txt（docx 也可以，但关键信息不以纯图片承载）
- [ ] 全文引号已统一为直引号
- [ ] 章节、流程事件、规则条目均有编号
- [ ] 业务功能名称全文逐字一致
- [ ] 六要素齐一份（见第二步模板）
- [ ] 排除项已显式列出
- [ ] 数值、公式、枚举已写明；确实定不了的标注「待 XX 阶段确认」并给出验证方向
- [ ] 流程图有等价的文字步骤
- [ ] 跨业务功能引用都带编号或文档名
- [ ] 「待澄清」事项集中列在一处（进入测试流程后会逐条登记回复）
