# 产品需求文档（PRD）编写约束要求

> **用途**：需求作者撰写与交稿自检；测试点/用例生成流程的受理与质检基准（S1 目标确定、S2 PRD 质检）。
> **总基准**：写到「能判对错」即可——每条规则说清谁、在什么条件下、做什么、怎么算成。字段枚举、边界值、页面文案属用例级细节，不作硬性要求。
> **流程约定**：PRD 定稿后全流程锁定，流程内不改文件；发现的问题一律靠澄清/补充说明解决并登记留痕。
> **示例约定**：全文示例统一采用贷款业务场景。本文档为需求侧交付物，供随需求模板下发；流程侧判据以 `.opencode/skills/prd-quality-check/` 为权威源。

## 一、业务功能：身份与界定

**业务功能 = 业务价值链（业务领域 → 业务活动 → 业务功能）中已收录、或经确认可收录的节点。** PRD 不产生功能，只是功能的**本次需求描述**：价值链已有 → 对齐引用；查无 → 请用户三选一（归入既有功能 / 确认收录新功能，之后才拟功能码 / 不属业务功能）；PRD 用词与价值链不一致 → 裁定映射后，全流程按登记名称引用。

**界定四问**（全答「是」才算一个业务功能）：

1. **对得上价值链吗？**——查无先确认收录，不从 PRD 直接造
2. **说得清目标吗？**——一句话讲明「谁用它达成什么」（贷款审批 = 审批人员对申请作出通过/拒绝结论）
3. **判得了对错吗？**——有可观察的完成标准（「系统高效处理贷款业务」立不成功能）
4. **边界闭合吗？**——定义在别处的操作能点名被引功能（审批页「放款」按钮，规则在 FUNC-05）

切分一条线：不同业务目标、或明文规定不同规则/结果才分立功能；字段、页面、校验项不另立（金额/期限/用途校验同属「贷款申请」）。

**需求描述 · 最低信息集（7 项）**：① 业务目标 ② 范围+排除项 ③ 参与角色 ④ 前置条件 ⑤ 结果方向+主要分支 ⑥ 外部依赖 ⑦ 引用他功能。**①②⑤ 是硬底线，缺一即 Blocker。**

**规范示例**（一份合格的「贷款申请」描述，括号标对应项）：

> **3.2 贷款申请（FUNC-01）**
> 借款人（③）可提交贷款申请（①），须填写金额、期限、用途；提交成功后生成「待审批」记录（⑤）。单笔超 50 万元转人工审批通道（⑤·分支）。受理金额 1,000–500,000 元、期限 3–36 期（②）；不含展期（见 FUNC-06）与提前结清（见 FUNC-07）（②·排除、⑦）。提交依赖征信系统查询授权通过（⑥）。前置条件：已完成实名认证并绑定银行卡（④）。

## 二、内容要求（五维 · 正反例）

| 维度 | ✅ 正例 | ❌ 反例（会被登记） |
|---|---|---|
| 完整性 | 「提交申请须填金额、期限、用途，成功后状态『待审批』；超 50 万转人工」 | 「本模块支持贷款申请」——无结果方向，出不了可判定的测试点 |
| 一致性 | 全文统一「借款人」，状态枚举唯一：「待审批/通过/拒绝/已放款」 | 3.1「当日放款」vs 4.2「T+1 放款」——同一对象两条规则，带「待核验」标记也须登记 |
| 无二义性 | 「月收入低于月还款额 2 倍的申请自动拒绝」 | 「资信不佳从严掌握」——拒绝还是降额？两种互斥理解 |
| 可测试性 | 「审批拒绝的申请在借款人端展示『已拒绝』状态」 | 「系统应安全稳定」——说不出看什么判过不过；注：未给性能数值不算缺失 |
| 可追溯性 | 展期规则挂 5.2 节，并写明「不含提前结清，见 FUNC-07」 | 利率规则散落全篇无编号，与营销说明混写——建不了锚点 |

## 三、问题分级与豁免

- **Blocker**：能力或通过标准无法确定（硬底线缺失、规则冲突、结果不可判）→ 澄清后才能推进
- **Major**：能出暂定测试点，但未决问题可能改变范围、拆分或验收结果
- **豁免三问**（全满足不算问题）：① PRD 声明有意留白/不设硬指标？② 给了验证方式？③ 不影响测试点的归组、拆分或判定？
- **「待核验」标记**：只吸收该条目自身未定部分；已写死内容之间的冲突照样登记

## 四、交稿自检（8 问）

1. 每个功能对上价值链了？查无的已提交确认？　2. 每个功能 7 项信息齐了吗？
3. 同一规则全文一个说法？　4. 条件、结果唯一，不产生两种理解？
5. 每项能力能判「通过/不通过」？　6. 范围与排除分得开、能定位原文？
7. 「待核验」没掩盖已写死内容间的冲突？　8. 定稿后不再改动？
