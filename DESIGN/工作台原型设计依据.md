# 测试用例工作台 · 原型设计依据

> **读者**：UI 设计师。**用途**：为「测试用例工作台」原型设计提供业务依据——画什么、放什么、怎么交互。
> **来源**：仅依据仓库 `DESIGN.md` 整理；术语与流程定义以原文件为准（测试点 / 测试用例的权威定义见 `.opencode/skills/test-point-spec`、`test-case-spec`，本文只转述要点）。
> **阅读顺序**：先读设计总纲，第 1~3 节定流程与交互，第 4~5 节定内容与状态，第 6~7 节定结构，第 8 节定约束，第 9 节随查随用。

---

## 设计总纲：一切围绕「一个业务功能」组织

**三句话定调：**

1. **任务单位是功能**。每次任务 = 项目 + 一个目标业务功能。任务开始时，系统从 PRD 列出功能清单（名称逐字取自 PRD 原文），用户只选定**一个**目标功能。
2. **界面常驻功能上下文**。选定之后，S2~S9 每一屏顶部都挂着该功能名，所有产物、检查记录、测试用例都归属这个功能；功能名是全界面的"地址牌"。
3. **换功能必须显式挂起**。同一时刻界面只有一个功能处于激活态；要去做别的功能，先在任务账本登记挂起，再从功能清单另起任务。

这条边界是整个信息架构的根：导航、进度条、台账、弹窗，全部长在「当前功能」这根枝干上。

## 1. 一页速读：这是什么系统

**一句话**：用户交来研发资料，系统里一个「AI 测试专家团队」分 9 个阶段，把它变成每条都能指回 PRD 原文的测试点（TP）与测试用例（TC）。

| 环节 | 内容 |
|---|---|
| 输入 | 项目目录下的研发资料：产品需求文档（PRD）、开发设计文档、数据字典。界面里**只可查看，不可编辑** |
| 处理 | 9 个阶段、5 处人工门禁（用户不确认不推进）、2 条质检修复循环（自动往返） |
| 输出 | 测试点清单、测试用例清单、各阶段质检报告、覆盖对照表 |

**界面上的角色分工（用户视角）**：

| 角色 | 在界面上长什么样 |
|---|---|
| 用户（现实中的人） | 唯一对话对象是「测试经理」；5 处门禁都由用户拍板 |
| 测试经理 | 主持人与对话者：安排阶段、请用户确认、汇报状态 |
| 测试设计专家 | 后台执行者：生成测试点、用例，修复质检问题。界面需显示"此步的执行者是他" |
| 测试质检专家 | 后台执行者：只检查、不修改、不与用户对话。界面需显示"此步的检查者是他" |

**给设计师的一个定调**：这套流程的"重"是产品价值，不是流程噪音——生成与检查分属两个后台角色，是为了防止自己检自己走过场；每条测试点挂 PRD 摘录，是为了说得出依据；门禁强确认，是为了防止"嗯、先继续"被当成同意。原型请如实呈现这些"笨拙但可靠"的机制，不要为顺滑而弱化。

## 2. 主流程主线：9 个阶段 × 5 处门禁

文字版流程（先看节奏）：

```
S1 目标确定 ─◆G1 确认目标功能
→ S2 PRD质检 ─◆G2 问题处置
→ S3 测试点识别 ⇄ S4 测试点质检（质检修复循环）
   通过 → ◆G3 测试点验收（S5）
→ S6 设计材料质检 ─◆G4 缺失项处置
→ S7 用例生成 ⇄ S8 用例质检（质检修复循环）
   通过 → ◆G5 用例评审（S9）→ 完成
```

◆ = 人工门禁（强确认，不通过不推进）；⇄ = 质检发现问题 → 回到生成方修复 → 复检，按轮次往返。

**阶段对照表**：

| 阶段 | 后台执行者 | 一句话做什么 | 画面落点 | 界面产物 |
|---|---|---|---|---|
| S1 目标确定 | 测试经理 | 读 PRD、列功能清单（名称逐字原文+拟功能码）、确定目标功能、登记引用链与锚点底册、生成 PRD 快照 | 功能落地页 + G1 弹窗 | 01-scope.md、00-input/prd.txt、00-state.md |
| S2 PRD 质检 | 测试质检专家 | PRD 五维体检（完整性/一致性/无二义性/可测试性/可追溯性）+ 漏锚扫描 | 问题清单页 + G2 弹窗 | 02-prd-check.md |
| S3 测试点识别 | 测试设计专家 | 先广撒网列全覆盖维度，收敛为业务级测试点 | TP 台账（草稿态） | 03-test-points.md |
| S4 测试点质检 | 测试质检专家 | 逐条语义核对 + 脚本形式校验 | 质检修复循环页 | 03-tp-check.md（按轮次）；通过后 03 定稿 |
| S5 测试点验收 | 测试经理 | 请用户把测试点清单确认为基线 | 门禁确认弹窗 | 03 标注「已验收」 |
| S6 设计材料质检 | 测试质检专家 | 检查设计文档/数据字典能否支撑用例生成；有缺口如实标出；流程图等不可解析内容显式登记缺失项 | 问题清单页 + G4 弹窗 | 04-design-check.md |
| S7 用例生成 | 测试设计专家 | 基于验收测试点与已确认材料产出十字段用例 | TC 台账（草稿态） | 05-test-cases.md |
| S8 用例质检 | 测试质检专家 | 逐条核对 + TP 全覆盖校验 | 质检修复循环页 | 05-tc-check.md（按轮次）；通过后 05 定稿 |
| S9 用例评审 | 测试经理 | 最终确认，登记完成 | 门禁确认弹窗 | 05 标注「已评审」 |

**进度条设计建议**：9 节点横向流程条，门禁相邻节点（G1~G5）用强调样式；当前阶段只亮一个；退回时按下节去向表回退，已完成阶段保留"曾经通过"的痕迹（如变灰的对勾），避免用户误以为之前的工作凭空消失。

## 3. 门禁交互：用户拍板的 5 处

### 3.1 三种法定答复（不可增减，界面上不要做同义变体）

| 答复 | 含义 | 界面形式建议 |
|---|---|---|
| `通过` | 确认无异议，继续下一阶段 | 主按钮 |
| `调整@<编号> <说明>` | 指定条目修订；修订后自动送质检复检，轮次 +1 | 逐条「调整」入口 + 说明输入框 |
| `退回` | 推倒重来，按 3.3 去向表回退 | 次级/警示按钮 |

- 任何其他措辞（"嗯""先继续""OK 吧"）**一律不算确认**。弹窗与输入区文案必须明示这一点，输入框占位符建议直接写出三种答复格式。
- 「调整」不是免检通道：修改后的产物必须经质检复检，界面应显示「调整 → 复检中」的过程，而不是静默变绿。

### 3.2 Blocker 带风险推进的二次确认

问题清单里有 Blocker 而用户仍想推进时，须二次确认（答复格式「通过 + 阶段名」）。原型需要设计二级弹窗：大字标明"存在 Blocker，是否带风险推进"，并要求再次答复阶段名。

### 3.3 门禁退回去向表（进度条回退的依据）

| 门禁 | 退回后回退到 | 典型原因（可直接用作弹窗提示文案） |
|---|---|---|
| G1 确认目标功能 | 重做 S1 | 功能清单或目标选得不对 |
| G2 问题处置 | S1 | PRD 问题太重，需重新确定目标 |
| G3 测试点验收 | S3 | 测试点不认可，重新识别（改后必经 S4 复检） |
| G4 缺失项处置 | S5 | 需要重新确认测试点基线 |
| G5 用例评审 | S7 | 用例不认可，重新生成（改后必经 S8 复检） |

### 3.4 门禁弹窗的通用结构

两块内容必须出现：① 本次要确认的**产物定稿摘要**（不能让用户凭记忆批准）；② 当前**挂着的待决问题**（无则明示"无待决问题"）。动作区 = 三种答复 + （有 Blocker 时）风险提示与二次确认层。

## 4. 核心对象素材：测试点与测试用例

### 4.1 一句话分清

| | 测试点（TP） | 测试用例（TC） |
|---|---|---|
| 回答什么 | **验证什么**业务能力 | **具体怎么验** |
| 长什么样 | 验证意图 + PRD 依据（锚点 + ≤40 字摘录） | 前置条件、测试数据、操作步骤、预期结果 |
| 关系 | 一条 TP 派生一至多条 TC（超 10 条须写明原因） | 每条 TC 只挂一个 TP |

### 4.2 TP 卡片（台账行的信息结构）

| 元素 | 说明 |
|---|---|
| 编号 | `TP-<功能码>-NNN`；编号只增不改不复用 |
| 名称 | 「验证 + 对象 + 结果方向」，≤30 字；对象直接用 PRD 原词 |
| PRD 锚点 | 定位到 PRD 原文某一句 |
| 原文摘录 | ≤40 字、**逐字**来自 PRD（机器校验），验证的事就是该句原文说的事 |
| 状态 | 草稿 / 已定稿 / 已验收 |

**溯源是 TP 的视觉中心**：建议把摘录做成可点击的引文样式，点击跳到 PRD 快照对应原句——"点得回去"是这个产品的招牌体验。

**正误示例（可直接用作原型示例数据）**：

| 示例 | 判定 |
|---|---|
| 验证超单笔限额的转账被拒绝 | ✅ 一条逻辑、一个结果方向、PRD 原词 |
| 验证转账功能正确 | ❌ 多条规则塞一条，判不了 |
| 验证输入 0 元和负数均被拒绝 | ❌ PRD 对两者同规则，具体数据是用例的事 |

### 4.3 TC 明细（十字段）

| 字段 | 内容要点 |
|---|---|
| 编号 | `TC-<功能码>-NNN` |
| 标题 | 「场景 + 预期」，如"金额超单笔限额，交易拒绝并提示" |
| 关联 TP | 单个 TP 编号 |
| 优先级 | P0 核心主流程 / P1 重要分支与边界 / P2 次要场景 / P3 罕见与健壮性 |
| 前置条件 | 可构造的具体状态，禁止"系统正常"类空话 |
| 测试数据 | 具体值，金额/字段给到具体数值 |
| 操作步骤 | 动词开头、编号分步 |
| 预期结果 | 可判定的具体值/文案/状态，多个结果分点写 |
| 用例类型 | 正向 / 反向 / 边界 / 异常 / 流程 |
| 变更状态 | 预留字段，当前流程一律留空（原型可显示为灰色占位列） |

**视觉分级建议**：优先级 P0~P3 → 红/橙/蓝/灰四档徽章；用例类型五枚举各给固定色全站一致（如正向=绿、反向=琥珀、边界=紫、异常=红、流程=蓝）。类型交叉时按 边界>异常>反向>流程>正向 取首个命中，徽章只显示一个。

**两种「未覆盖」要专门设计（是合法登记，不是缺漏）**：

| 情形 | 界面表现 |
|---|---|
| 某 TP 因材料缺口未生成 TC | 标注「S6 缺失项 <编号>」与豁免原因；材料补齐后可恢复生成 |
| TP 全覆盖豁免 | 覆盖对照表里显式填写"未覆盖原因"（非空非占位），否则机检直接失败 |

### 4.4 覆盖对照表

两组对照：S4 产出「锚点 → TP」、S7 产出「TP → TC」。每行必填，未覆盖必须写原因，禁止留空。UI 上建议给覆盖率统计（如"锚点 12/12 已建点""TP 30/35 已生成用例"）+ 豁免原因列；某 TP 下 TC 超 10 条时显示原因标注。

## 5. 状态与徽章系统

### 5.1 功能（任务）级状态

| 状态 | 进入时机 |
|---|---|
| 待开工 | 功能清单里的候选（名称来自 PRD 逐字原文 + 功能码徽章），尚未选定 |
| 进行中 | G1 通过，S2 起跑 |
| 已挂起 | 用户切换功能时显式挂起（在 00-state 登记） |
| 已完成 | G5 用例评审通过 |

### 5.2 产物文件状态流

```
草稿（生成完成待检）→ 质检中 → 修复中（第 N 轮）→ 已定稿 → 已验收(03, S5后) / 已评审(05, S9后)
```

01 底册建立并验收后冻结（唯一例外：漏锚扫描确认补录）；00-state 是任务账本，开工先读它并与各产物条目数核对，不一致先求证。

### 5.3 问题徽章

| 级别 | 含义 | 颜色建议 |
|---|---|---|
| Blocker | 没法定义或判定的硬伤 | 红 |
| Major | 可暂定，但未决问题可能改变范围、拆分或验收结果 | 琥珀 |

不影响生成与判定的细节不进问题清单——界面不要为小问题刷存在感。

**两类问题去向不同，交互差异大**：

- **产物级** → 自动走修复循环（轮次 +1），用户看得到轮次在走；
- **输入/基线级**（PRD 歧义、材料缺口、TP 基线错误）→ 循环**立即暂停**，升级呈报用户裁定。界面给"需要你裁定"的醒目插页，不是普通问题行。

### 5.4 轮次与留痕

质检报告按轮次追加、不覆盖历史；同一质检阶段连续 3 轮未收敛，系统自动暂停请用户裁定。UI 对应：对话流 / 报告页显示「第 N 轮」标签；触发收敛保护时给专门的裁定卡片。

### 5.5 模式标识

**演示模式**（默认，不写文件，产物在对话内逐字呈现）与**落盘模式**（写全套产物并跑机器校验）。两模式执行路径完全一致，界面布局不变，只换醒目的模式标识；演示模式下机检降级为对话内声明，相关徽章可注记"声明通过（非机检）"。

## 6. 信息架构：项目 → 业务功能 → 产物

**真实文件层级（原型信息组织的原型）**：

```
项目（qa-workspace/<项目名称>/）
├─ 材料目录（只读）：产品需求文档 / 开发设计文档 / 数据字典
└─ <功能码>-<功能名>/        ← 每个功能一个任务目录
   ├─ 00-state.md           任务账本（状态恢复的依据，开工先读）
   ├─ 01-scope.md           范围与锚点底册（冻结后为全流程溯源依据）
   ├─ 00-input/prd.txt      PRD 文本快照（机器生成，摘录逐字校验的基准）
   ├─ 02-prd-check.md       S2 质检报告
   ├─ 03-test-points.md     TP 台账
   ├─ 03-tp-check.md        S4 质检报告（按轮次）
   ├─ 04-design-check.md    S6 质检报告
   ├─ 05-test-cases.md      TC 台账
   └─ 05-tc-check.md        S8 质检报告（按轮次）
```

**导航建议（供发散的参考布局，不是限定方案）**：

- 顶层：项目内业务功能任务列表——功能卡片带状态徽章（待开工/进行中/已挂起/已完成），卡片名称永远逐字显示 PRD 原文
- 任务工作区：常驻"功能上下文头"（功能名 + 功能码 + 模式标识），下方三区 —— ① 阶段进度条；② 当前阶段面板（对话或操作流）；③ 产物侧栏
- 面包屑永远停在功能上：`项目 / 功能名 / 当前阶段`
- 产物侧栏把文件分两组：**台账类**（01 / 03 / 05，是"内容"）与**报告类**（02 / 03-tp-check / 04 / 05-tc-check，是"体检单"）
- 材料入口标注「只读」；PRD 显示「版本锁定」徽章（S1 后锁定，每次开工自动核对指纹，不一致即暂停并请用户二选一：恢复原 PRD / 从 S1 重新开始）

**写权限在界面上的投影**：用户不能直接编辑台账与报告（内容由后台产出、机器校验兜底）；用户能做的是**选择、确认、按格式答复、任务级操作（挂起/切换/查看）**。锁形标识可用于只读区。

## 7. 关键画面清单（原型必画）

10 个画面覆盖全流程；**加粗 5 个为最小可演示集**：①②④⑥⑦。

| # | 画面 | 目标 | 必备元素 |
|---|---|---|---|
| ① | **功能落地页** | 选定目标功能 | 项目名；PRD 功能清单（名称逐字 + 功能码徽章）；功能状态区分（待开工/进行中/已挂起/已完成）；最近任务入口 |
| ② | **任务工作台（常驻）** | 单功能滚动推进的全过程 | 功能上下文头（功能名+码+模式标识）；9 阶段进度条与门禁样式；当前阶段执行者；产物侧栏 |
| ③ | G1 确认目标功能 | 流程第一次拍板点 | 功能清单摘要；锚点底册与引用链登记说明 |
| ④ | **门禁确认弹窗（通用）** | 5 处共用结构 | 定稿产物摘要；待决问题；`通过/调整@编号/退回` 三动作；Blocker 二次确认层 |
| ⑤ | 问题清单页（S2/S6） | 呈报体检结果 | 五维问题条目；Blocker/Major 徽章；处置建议；输入级问题「需你裁定」插页；S2 专属：漏锚扫描结果与补录确认 |
| ⑥ | **TP 台账** | 把关验证目标 | 编号/名称/锚点摘录（引文样式）/状态；锚点→TP 对照入口；摘录点击跳 PRD 原句 |
| ⑦ | **TC 台账** | 最终交付物 | 十字段明细（表格或卡片）；TP→TC 对照与覆盖统计；豁免标注；某 TP 下 TC 超 10 条的原因标注 |
| ⑧ | 覆盖对照表 | 覆盖与豁免的全景 | 锚点→TP、TP→TC 两组；覆盖率统计；未覆盖原因列（禁止留空的空态引导） |
| ⑨ | 质检修复循环页（S4/S8） | 展示"过手即留痕" | 问题 → 修复 → 复检的轮次时间线；「第 N 轮」标签；连续 3 轮未收敛的裁定卡 |
| ⑩ | 挂起与切换 | 换功能的合法通道 | 切换前确认；挂起登记提示；回任务列表 |

## 8. 设计约束（交互边界）

1. **单功能激活**：同一时刻只有一个业务功能处于激活态；其余功能的入口只提供查看与挂起恢复，不提供编辑操作，也不做跨功能的批量操作。
2. **双模式同构**：演示 / 落盘两模式界面布局一致，只换模式标识与产物载体说明，不让用户猜差异。
3. **材料只读**：PRD / 开发设计文档 / 数据字典仅可查看；PRD 一经 S1 即版本锁定，之后界面上任何"改 PRD"的入口都不该存在。
4. **答复即协议**：门禁只认三种答复；输入区要示范格式；模糊措辞界面应拦截并提示"未确认"。
5. **全程留痕**：确认记录、澄清登记（用户口头澄清的结论落登记处，登记后可作 TP 依据）、质检轮次都是追加不覆盖；不要做"覆盖历史"的交互。
6. **无删除**：系统不执行删除类命令——原型不提供"删除产物"按钮；弃用走退回 / 挂起 / 受控变更（失效、新增、修改标记；编号只增不改不复用，禁止无差别重新生成）。
7. **文案纪律（表达四原则）**：精炼忌冗长、准确忌歧义、浅显忌黑话、边界明确忌模棱两可。每句提示都应能回答"现在能做什么、不能做什么"。
8. **单功能边界收口**：即使是多任务列表，列表页也只是"入口"；所有生成、质检、确认动作都发生在某个功能的工作区内部。
