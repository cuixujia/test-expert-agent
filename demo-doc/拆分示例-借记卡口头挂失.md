# 拆分示例：从 PRD 原文到测试点与测试用例（借记卡口头挂失）

> 用途：与团队对齐「业务功能 → 测试点 → 测试用例」的拆分思路。
> 对齐口径的唯一锚点是 **PRD 原文**，每一步判定规则来自定义而非个人经验。
> 本示例基于模拟 PRD 编写，仅用于示范拆分方法。

---

## 一、业务功能

| 项 | 内容 |
|---|---|
| 所属模块 | 3 账户服务 |
| 业务功能 | 3.2 借记卡口头挂失 |
| 功能码 | GS（仅用于 TP/TC 编号，不替代名称） |
| 一句话说明 | 客户对本人借记卡发起临时挂失，挂失即时生效阻断交易，可柜面解挂恢复，到期未解挂自动转正式挂失 |

**PRD 原文（对齐口径的唯一锚点，争论回到这几句话上）：**

> **3.2.1** 客户可通过手机银行或柜面对本人借记卡发起口头挂失，挂失自提交成功起立即生效。
> **3.2.2** 挂失生效后，该账户的取款、转账、消费功能均不可用，系统应拒绝并提示“账户已挂失，请先解挂”。
> **3.2.3** 口头挂失期间，客户可凭本人有效身份证件在柜面办理解挂，解挂成功后账户功能立即恢复；口头挂失有效期为 5 天，第 5 天日终批处理后仍未解挂的，自动转为正式挂失。

## 二、测试点清单

| 编号 | 验证意图 | 类型 | 分析方法 | 依据 |
|---|---|---|---|---|
| TP-GS-001 | 验证口头挂失提交成功后立即生效 | 功能 | 场景法 | 3.2.1「挂失自提交成功起立即生效」 |
| TP-GS-002 | 验证口头挂失期间交易被拒绝并提示解挂 | 功能 | 场景法 | 3.2.2「该账户的取款、转账、消费功能均不可用，系统应拒绝并提示」 |
| TP-GS-003 | 验证柜面解挂成功后账户功能立即恢复 | 流程 | 状态迁移 | 3.2.3「解挂成功后账户功能立即恢复」 |
| TP-GS-004 | 验证口头挂失期满未解挂自动转正式挂失 | 流程 | 状态迁移、边界值 | 3.2.3「第 5 天日终批处理后仍未解挂的，自动转为正式挂失」 |

### TP 层对齐要点

1. **按业务目标收拢**：3.2.1 的手机银行和柜面是同一能力下的并列办理渠道，合为 TP-GS-001；3.2.2 的取款、转账、消费是并列交易类型，处理结果相同，合为 TP-GS-002。渠道和交易类型分别由测试用例覆盖。
2. **不同业务结果分别成点**：3.2.3 的柜面解挂后恢复功能，与期满后自动转正式挂失，是两种不同结果，因此分别形成 TP-GS-003、TP-GS-004。
3. **不按测试点数量凑覆盖**：字段、渠道、交易类型和日期边界是覆盖维度，不自动各自形成 TP；测试用例覆盖这些维度。
4. **不把经验猜测当需求**：重复提交幂等未写入这段 PRD，不能仅凭银行惯例列为已确认 TP。如业务方确认需要验证，再作为需求补充或经确认的风险项处理。
5. **TP 只表达业务验证目标**：不写具体数据、步骤或提示文案；这些由测试用例承接。

### TC 层对齐要点

1. **一个 TP 可对应多条 TC**：TP-GS-001 合并手机银行和柜面两个并列渠道，由两条 TC 覆盖；TP-GS-002 合并三种交易类型，由三条 TC 覆盖。每条 TC 只执行一个渠道或交易场景。
2. **TC 数量由执行覆盖需要决定**：同一 TP 中，如果不同条件需要不同入口或步骤，应分别执行；若只是换数据且一次执行能覆盖同一要求，不必机械增加 TC。
3. **TP 不写具体文案和数据**：「账户已挂失，请先解挂」来自 PRD，写在 TC 预期结果；文案变化通常只影响 TC，不改变 TP 的业务目标。
4. **一条 TC 只验证一个目的**：本例拒绝交易的 TC 只验证对应交易被拒绝并提示，不额外断言 PRD 未规定的余额变化、手续费或告警日志。

## 四、收拢口诀（速查）

> **TP 问：产品要确认哪些业务目标？**
> —— 同一业务能力下的并列条件收拢为一条；不同目标或 PRD 明确规定不同流程、规则、权限、结果时拆分；没说清时先合并并记录待澄清问题。

> **TC 问：需要哪些执行场景，才能覆盖 TP 所含要求？**
> —— 按入口、步骤、数据和结果覆盖明确要求；一条 TC 只验证一个目的，同一 TP 可关联多条 TC。

> **TP:TC = 1:N**：TP 按业务目标收拢；TC 按覆盖需要展开。TP 数量不作为目标。
