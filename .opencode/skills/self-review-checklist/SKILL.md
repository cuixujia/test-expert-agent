# 产出核验与结论口径——唯一定义源

**职责边界**：装「怎么核、结论怎么判、产出怎么写、脚本怎么用」；不装 TP/TC 定义与判据（见 test-point-spec / test-case-spec）、资料清单（见 tdd-quality-check）、需求证据规则（见 prd-quality-check）、分析方法（见 test-analysis-methods）。

## TP 核验（语义核对，逐项执行、只报异常）

1. **证据核对**：逐条核对锚点定位正确、摘录确实支撑该验证目标；「PRD 没写、推出来」的按三要素核对（来源已注明/挂最相关原文/不与明文矛盾）；用户澄清结论（CL 编号）作依据的与澄清内容不矛盾。摘录逐字一致性不再人工核对——validate.sh 机验保证
2. **切分核对**：合并/拆分合规、三违规（太大/太小/耦合）不出现
3. **归组边界核对**：没有把不同业务目标或 PRD 明文规定的不同处理硬合在一起，也没有把同一业务目标重复拆成多条 TP
4. **命名核对**：「验证」+ 对象（PRD 原词）+ 结果方向，无预期细节与步骤
5. **可判定核对**：每条答得出「看什么分过/不过」；答不出记问题（Blocker）
6. **高风险判定**：非功能型 TP 的取舍依据（PRD 提及/高风险）明确合理
7. **覆盖核对**：以 scope.md 锚点底册为底册逐锚点核对覆盖**实质完整**（不能只因锚点有 TP 就算覆盖）；范围外或不覆盖的须有显式原因（如流程图不可解析 / 非目标功能范围 / 用户确认不测）。覆盖表↔TP 依据的**双向映射一致性由 validate.sh 机检**，不人工核对留痕
8. **去重**：同一意图重复 TP 记问题（产物级）
9. **名称一致**：清单标题与正文引用的模块/功能名称与底册登记原文逐字一致

## TC 核验（语义核对，逐项执行、只报异常）

1. **字段完备**：十字段逐项非空；变更状态一律留空
2. **溯源完整**：关联 TP 均真实存在于已验收清单；TP↔TC 覆盖对照表未覆盖项有显式原因——常规核验通过后所有 TP 均须覆盖，仅用户明确批准的风险推进/不测决定可豁免（须核对状态文件中的澄清/风险记录，不能仅凭非空原因放行）。**前端或后端等必需资料问题未解决时，不得以覆盖豁免代替资料补齐**
3. **比例提醒**：单 TP 派生 TC 超 10 条，留痕说明原因，不硬禁
4. **步骤可执行、预期可判定、单一目的**：按 test-case-spec 质量标准核对；混合意图的拆分修复
5. **领域复核**：对照 test-analysis-methods 领域检查单补遗漏（银行：金额精度/幂等/权限；接口：异常码/超时重试）
6. **名称一致**：标题与正文引用的模块/功能名称与底册登记原文逐字一致

## 问题分级与处置方（唯一权威源，报告必标）

| 标注 | 取值 | 判定 |
|---|---|---|
| 级别 | Blocker / Major | Blocker = 无依据或无法判定；Major = 可修的形式与粒度问题，或未决问题可能改变范围/拆分/验收结果 |
| 处置方 | 产物级 / 输入·基线级 | 产物级 = 生成者可修，走修复循环；输入·基线级 = PRD 歧义、材料缺口、基线错误——**立即暂停修复循环呈报用户**，禁止在循环内硬编硬造 |

- **各环节的判定口径**（同一级别在不同环节看不同后果）：需求资料质检看「业务能力或通过标准是否可确定」→ 无法确定=Blocker、可暂定但可能改变范围=Major；用例生成资料质检看「受影响 TP 的用例是否无法生成或预期无法判定」→ 无法生成/无法判定=Blocker、可暂定但缺口会改变步骤·数据·预期=Major；产出核验看上表
- 三处报告（prd-check / design-check / tp-check·tc-check）统一按本节标注级别与处置方

## 表达与报告规范（唯一权威源）

### 表达四原则（面向用户的一切对话与产物正文）

- **精炼忌冗长**：一句话说清，不铺陈；结论先行
- **准确忌歧义**：不用「基本」「大概」「可能」等模糊词；判定性内容给可判口径
- **浅显易懂忌黑话**：禁用比喻性、学术性、黑话词（如：张力、抓手、赋能、心智）；「口径」类词换成「说法/规则/标准」
- **边界明确忌模棱两可**：说清适用范围与例外；不写「视情况而定」

**术语白名单**：只使用框架已定义术语（测试点 TP、测试用例 TC、锚点、门禁、Blocker、Major、功能码、质检、派发等）与 PRD 原文用词；**禁用口语变体**——「测试项」「检查点」「用例点」不得出现在任何产出中，「质检」不写成「自检」。

**问题描述句式**：「现状（哪里写了什么）→ 差异/缺失 → 影响」，一句话说清；反例：「两条规则存在口径张力」；正例：「两条规则说法不一致：一条说按项目归属判断可见范围，另一条说普通测试人员只能看自己创建的风险」。

### 报告瘦身铁律

- 只写结论性发现，不逐条罗列「检查过且无问题」；不设候选判定留痕、挑战位等过程性附录
- 复查轮次每条复核结论一行（`问题编号：已消解（核对点+脚本 PASS）`），禁止重贴摘录、行号与修复后全文
- 问题清单主表只登记未消解问题

## 修复与复检约定

- 修复只处理问题清单列出的产物级问题及直接影响项；保留无关已验收内容；编号只增不改，删除仅标记废弃
- 每次修复在产物尾部「质检记录」表留痕（一行一条）：

```markdown
## 质检记录
| 轮次 | 问题编号 | 修复动作（一句话） |
|---|---|---|
```

- **闭环禁令**：禁止只报告不修复、只修复不复核；禁止产物级问题未经修复直接复检通过
- **修复后自检（FAIL 清零才交回）**：修复落盘后重跑 validate.sh 对应模式，把「修复引入新问题」挡在复检之前
- 复检在原报告追加一小节，不覆盖历史；复核结论按「表达与报告规范」一行式书写
- 修复循环上限 3 轮：仍有未解决问题 → 列明双方依据呈报用户裁定
- **覆盖对照表模板**：TP 与 TC 的列结构分别见 test-point-spec / test-case-spec 的清单模板节，本 skill 不重述

## validate.sh 用法（必跑）

机械校验分层：生成者交稿前跑对应模式并返回退出码与产物 SHA-256；流程编排方收回时核对退出码、条目数与 SHA-256；核验者对最终产物正式校验并把退出码写入报告。文件未变化时不重复跑同一校验。

```bash
V=".opencode/skills/self-review-checklist/validate.sh"
# TP 清单核验（含编号/字段/锚点引用/底册全覆盖/覆盖表↔TP依据双向映射/摘录逐字机验）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>" test-point
# TC 清单核验（含十字段/TC→TP引用/TP全覆盖含豁免）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>" test-case
# 状态文件校验（登记项固定唯一/确认记录格式/CL 编号唯一/指纹格式）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/state.md" state
```

- 目录推导：会话目录（`<uuid>`）内取 scope.md/state.md；功能目录（上一级）取 prd.txt 与 output/ 产物
- 判读：退出码 0 = 通过；非 0 = 有 FAIL，必须修复后重跑，禁止带 FAIL 定稿
- 覆盖豁免：脚本只检查未覆盖原因已填写；是否获用户批准由核验者核对状态文件决定
- `all` 模式仅限人工调试，正式核验禁止使用
- **需求与证据侧校验（快照、底册、摘录提取、漏锚扫描、原文抄写）用 prd-quality-check/validate-prd.sh**，本脚本不依赖它

### 校验项清单（脚本实现，语义关依赖这些结论）

| 校验域 | 校验内容 |
|---|---|
| 锚点底册 | 清单存在且非空；锚点格式合规（建册即拦）；TP 依据锚点全在底册；底册锚点全在覆盖对照表；覆盖表锚点不得超出底册（防幻觉锚点） |
| 编号与字段 | `TP/TC-<功能码>-NNN`；编号功能码段必须等于所在功能目录名（防跨功能串号）；编号唯一；验证意图以「验证」开头；必填字段非空；优先级 P0~P3；关联 TP 单值且格式合法 |
| 引用完整性 | TC 关联的 TP 必须真实存在于 test-point.md；未被任何 TC 覆盖且未声明未覆盖原因的 TP 判 FAIL |
| 覆盖对照表 | 章节必须存在；未覆盖项必须带原因；覆盖表↔TP 依据双向映射必须一致 |
| 摘录机验 | 底册摘录 ≤40 字且逐字命中功能目录 `prd.txt` 快照（比对前做空白规范化，含全角空格）；TP 依据必须包含对应锚点的底册摘录；快照缺失判 FAIL；scope.md 标注「快照机验：跳过（原因）」时降级跳过 |

### Linux 调用规范（照抄执行，禁止反复探路）

- validate.sh 必须保持 LF 行尾（`.gitattributes` 已约束）；统一用 `bash "<脚本路径>"` 调用，路径含空格必须加引号
- **Windows 环境路径规范**：bash 运行在 WSL/Git Bash 下，入参必须是 bash 可见的路径——相对仓库根（`workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>`）或 WSL 绝对路径（`/mnt/host/d/Project/<项目>/...`）；**禁止把 Windows 绝对路径（`D:\...`）传给脚本**（bash 看不见，只会回一行用法，调用方拿不到有效诊断）。Windows 绝对路径只用于 read/write/edit 文件读写工具。中文目录名原样传参；路径不确定先 `ls` 确认，不凭印象拼路径
- SHA-256 用 `sha256sum`；文件指纹用 `md5sum`（不使用 macOS 专有的 `shasum`/`md5 -q`）
- 脚本兼容提示：字符长度校验用 `wc -m`（awk 的 `length()` 在 C locale 下按字节计数）；中文串相等判断用正则或 `index()`，不要在 `LC_ALL=UTF-8` 下直接 `==`（会误判真）
- 临时校验脚本不落盘；同一批 FAIL 重复出现 2 次即停止重跑，如实移交流程编排方
- **命令级熔断**：同一条命令失败 2 次即禁止第三次原样执行，必须换做法（换路径写法 / 换参数 / 换模式）；连续 3 次失败 → 停止并如实报告编排方「问题 + 已试参数 + 实际报错」，禁止靠反复重试硬磨
- **批量读取，禁止逐行翻页**：通读材料**优先用 `read` 工具一次读完**；脚本仅在需要程序化定位/批量提取/机验时用，不是读文件的前置条件；同一模式连续调用超过 10 次即视为用法错误，必须换批量读法
- **运行环境可能是 BusyBox/Alpine**：`awk` 是 BusyBox awk（`awk --version` 会报 "unrecognized option"，不是 gawk）；本脚本只用 POSIX awk 特性（match/substr/split/getline/SUBSEP），可直接运行。**不要用 gawk 专有选项探测环境**
- **嵌套引号坑**：`bash -c '... awk "..." ...'` 三层嵌套时 awk 程序里的 `$`/`{}` 极易被吃掉（典型报错 `awk: cmd. line:1: Unexpected token`）。**正确做法**：一律直接调用现成脚本（`bash "<脚本>" "<参数>" <模式>`）；确需内联 awk 时，把 awk 程序写成**单引号**包裹、整体命令用**双引号**传给 `bash -c`；复杂逻辑写成 `.sh` 文件再执行，不要在命令行里拼多层转义
- **脚本 FAIL 的含义**：指**你的产物不合规**，不是脚本坏了。正确动作是按 FAIL 清单改产物后重跑；**禁止**读脚本源码后手工复现校验逻辑、**禁止**改脚本/skill 文件、**禁止**用探测命令反复验证环境——怀疑脚本缺陷时把「命令 + 完整输出 + 期望与实际差异」移交编排方
- **两份脚本的契约副本**：摘录比对口径（空白归一 + 剥 `「」` 摘录壳 + 长度 `wc -m`）在本脚本与 `prd-quality-check/validate-prd.sh` 中各有一份实现，**改一处必须同步另一处**（只改一处会导致同一份底册两个脚本结论相反）
