# 自检与评审清单

## TP 自检清单（S4，两关分工，逐项执行并留痕）

### 第一关 · 语义关（人工逐项，脚本无法替代）

1. **出处核对**：逐条 TP 按 test-point-spec「说得出出处」核对——锚点定位正确（摘录确实支撑该验证目标）；「PRD 没写、推出来」的按其三要素核对（来源已注明/挂最相关原文/不与明文矛盾）；两条都占不住的已按无依据处理。摘录与原文逐字一致不再人工核对，由 validate.sh 快照机验保证（见第二关）
2. **切分线核对**：逐条 TP 按 test-point-spec「切得不多不少」核对（合并/拆分是否合规、三违规是否出现）；描述不清的已默认合并**且该模糊点已记入 02-prd-check 问题清单**，通过标准无法确定的已标记待澄清
3. **归组边界核对**：按 test-point-spec 收拢原则核对——没有把不同业务目标或 PRD 明文规定的不同处理硬合在一起，也没有把同一目标重复拆成多条 TP
4. **命名核对**：按 test-point-spec「命名」核对——「验证」+ 对象（PRD 原词直取）+ 结果方向；无具体预期表现、步骤、数据
5. **可判定核对**：逐条回答 test-point-spec「判得了对错」的问题「真执行了，看什么能分出过/不过？」；答不出的回炉——要么先要求 PRD 澄清，要么按无依据不产出处理
6. **高风险判定**：非功能型 TP 的取舍依据（PRD 提及/高风险）明确合理
7. **覆盖反向核对**：以 01-scope.md 锚点清单为底册**逐锚点核对**；对已纳入范围的锚点，检查其下每条适用的明确要求都包含在对应 TP 的验证范围内，不能只因锚点有 TP 就判定该锚点覆盖完整；范围外或不覆盖的锚点须显式填写原因，产出覆盖对照表（原因示例：流程图不可解析 / 非目标功能范围 / 用户确认不测）
8. **去重合并**：同一意图重复 TP 合并；编号唯一
9. **名称一致性**：03 文件标题与正文引用的模块/功能名称与 01-scope.md 登记原文逐字一致（规则见 prd-quality-check）

### 第二关 · 形式关（validate.sh 必跑）

校验：编号格式与唯一性、验证意图以「验证」开头、必填字段、TP 依据锚点在底册、底册锚点全覆盖、（用例生成后）TC→TP 引用完整、TP 全覆盖。

**脚本 PASS ≠ 自检通过；两关都过才可提交 S5 验收。**

## TC 自检清单（S7，逐项执行并留痕）

1. **字段完备**：十字段（定义见 test-case-spec 字段规范）逐项非空；变更状态一律留空
2. **溯源完整**：关联 TP 均真实存在；产出「TP ↔ TC 覆盖对照表」，未覆盖 TP 必须显式填写原因
3. **比例提醒**：单个 TP 派生 TC 超过 10 条，须在自检记录表留痕说明原因（TP 过大或用例过碎），不硬禁
4. **步骤可执行**：按 test-case-spec 质量标准核对——入口具体、动词开头、无歧义词，第三方可照做
5. **预期可判定**：按 test-case-spec 质量标准核对——有具体值/文案/状态，可直接判 pass/fail
6. **单一目的**：一条用例一个验证目的，即一个 pass/fail 结论（判据见 test-case-spec 质量标准）；发现混合意图的拆分
7. **领域复核**：对照 test-analysis-methods 三大领域专项检查单，补齐遗漏（银行重点：金额精度/幂等/权限；接口重点：异常码/超时重试）
8. **名称一致性**：05 文件标题与正文引用的模块/功能名称与 01-scope.md 登记原文逐字一致
9. **形式关**：运行 validate.sh（01/03/05 全部校验项），全部 PASS 且 TP 语义关已经过，方可提交 S8

## 覆盖对照表模板

TP 覆盖对照表与 TC 覆盖对照表的列结构分别见 test-point-spec / test-case-spec 的清单模板节。

## 自检闭环（发现 → 修复 → 复核）

自检发现的每一处修复必须在 03/05 文件尾部「自检记录」表中留痕：

```markdown
## 自检记录
| 轮次 | 检查项 | 发现 | 修复动作 | 复核结果 |
|---|---|---|---|---|
```

禁止只报告不修复、只修复不复核。

## validate.sh 用法（必跑）

```bash
bash .opencode/skills/self-review-checklist/validate.sh qa-workspace/<功能目录> all
```

- 校验项：01 功能清单结构（模块名称/功能名称原文非空、模块/功能编号格式、功能码格式与唯一）、锚点清单底册（01-scope.md 锚点清单存在、TP 依据锚点全部在底册、底册锚点全部出现在覆盖对照表）、03/05 编号格式与唯一性、验证意图以「验证」开头、必填字段非空、TC→TP 引用完整性、TP 全覆盖（反向：未被任何 TC 覆盖的 TP）、覆盖对照表存在性与未覆盖项原因声明
- 摘录逐字机验（落盘模式）：01 底册原文摘录 ≤40 字且逐字命中 `00-input/prd.txt` 快照（比对前做空白规范化，含全角空格）；TP 依据必须包含对应锚点的底册摘录；快照缺失报 FAIL；01 标注「快照机验：跳过（原因）」时输出 WARN 并跳过（降级声明，规则见 prd-quality-check 锚点规则 9）
- 脚本兼容性注意：macOS awk 的 `length()` 按字节计数，摘录长度校验必须用 `wc -m`（LC_ALL=en_US.UTF-8）；且在 LC_ALL=UTF-8 下对纯中文串的 `==` 比较会误判真——validate.sh 的 awk 一律走 C locale 字节语义（不设 LC_ALL），中文相等判断用正则或 `index()`
- 判读：退出码 0 = 通过；非 0 = 自检不通过，**必须修复后重跑**，禁止带 FAIL 提交
- 单独校验：`01-scope.md` / `03-test-points.md` / `05-test-cases.md` 可作为第二参数单独传入
