# PRD / 设计材料五维质检

## 锚点规则（溯源基础，S1 起全程使用）

1. PRD **已有编号体系**（如 REQ-001、3.2.1）→ 直接使用原文编号作为锚点
2. PRD **无编号** → 按以下规则建立锚点：`M<模块号>-S<章节号>-P<段落号>`（如 `M1-S2-P3` = 模块1/第2章节/第3段落；无段落细分时 P0 表示整节）
3. **锚点清单表（目标功能确定后建立，全流程唯一溯源底册）**：S1 通读 PRD 并由用户选定目标功能后，在会话目录 `scope.md` 内仅为该功能及必要横切依赖建立锚点；一经 S1 验收全流程冻结。**唯一例外**：S2 漏锚扫描（见下文）发现的缺口经用户确认后受控补录，并在 `state.md`「变更登记」记录 `底册补录 v<N>`。不得在目标未定时为所有功能预建明细锚点。TP 的依据、覆盖对照表的核对单元均以本表为准（表结构见下方「scope.md 模板」）。

4. 底册保留原文摘录；TP 引用锚点时**必须附原文摘录**，防止幻觉依据。摘录统一 **≤40 字**（含底册行），取 PRD **连续原句、禁止跨段拼接**；摘录须逐字命中 PRD 文本快照（规则 9），由 validate.sh 机验。对话默认只呈现决策所需的功能范围和锚点摘要，不粘贴完整底册；用户要求详细内容时再展开。validate.sh 校验依据锚点均在底册内、底册锚点全覆盖
5. functions.md 登记的模块名称与功能名称必须为 PRD 原文逐字引用（含模块编号/功能编号），禁止缩写、简写、改写；functions.md 为全流程唯一名称源，后续产物（prd-check / test-point / design-check / test-case 标题与正文、对话输出）引用名称时以登记原文为准；一句话说明允许概括
6. **锚点去重**：底册按可独立支撑测试判定的原文信息建锚；不同章节语义重复且不增加目标范围、规则或结果信息时，只保留更具体/更权威的一条锚点，其余在需要时注明“由 <锚点> 覆盖”，不得重复收录。若重复段落存在独有条件或结果，须分别保留对应锚点。
7. **引用链轻登记**：S1 用户选定目标功能后，扫描目标功能的业务规则/业务界面/完成标准中每处对其他功能的引用及操作入口归属（如「编辑/复制/删除分别在 FUNC-04/05/06 定义」），逐项登记入锚点清单：锚点=被引功能编号，条目摘要=引用事项，原文摘录=引用处原句（≤40 字）；仅作 S2 检索入口，不展开被引功能全文。
8. **功能码注册表（functions.md，首次 S1 全量登记，validate.sh 校验契约）**：功能码在首次 S1 随功能清单一次性全量拟定（validate.sh 校验全表格式与唯一性），仅作 `TP-<功能码>-NNN` / `TC-<功能码>-NNN` 编号用途，不替代名称；登记后全局冻结不变，后续功能开工沿用、不得重拟。运行时工作空间重建或丢失时，先从 git 历史恢复 functions.md 沿用既有功能码，不得重拟（注册表随 git 持久化，跨会话不丢失）
9. **PRD 文本快照（首次 S1 生成）**：在需求目录生成 `prd.txt`（同 PRD 各功能共用一份），作为摘录逐字机验（validate.sh）与漏锚扫描的检索基准。生成方式：docx 用 `textutil -convert txt`（备选 pandoc），md/txt 直接复制；**禁止模型转写**（避免二次抄录失真）。**快照字符规范**：生成时统一引号归一（弯引号 “ ” ‘ ’ → 直引号 " '），归一后快照即全链路唯一字符基准——底册摘录、TP 依据、TC 文案引用一律以其为准；推荐用 `bash "<skill 路径>/../self-review-checklist/validate.sh" "<需求目录>" snapshot "<需求文档文件名>"` 生成（内置归一并输出源文件 md5；快照只读，已存在即拒绝重建）。**降级前消化义务**：内嵌图片/流程图等不可解析内容，降级前必须先尽力自行解读（解包 docx 提取图片并读图，结论以「AI 解读待确认」标注登入底册或 state.md），仅当无法解读且影响判定时才降级并交用户确认——禁止把系统能自行消除的不确定性推给用户。快照源文件为需求文档：需求目录下保留原文件名的软链接或唯一需求原件（多版本时以 S1 用户指定为准，PRD 版本锁定规则见 test-manager 工作铁律 6）。PDF/图片等不可文本化材料：在 scope.md 标题下写 `> 快照机验：跳过（<原因>）` 降级声明，摘录机验与漏锚扫描随之下降级。快照只读，不参与任何产出改写。

## S2 PRD 质检范围（以 TP 可定义为准）

S2 的目的不是把 PRD 检查到可以直接编写全部 TC，而是确认目标功能是否足以生成**有依据、范围清楚、结果可判定的业务级 TP**。保留五维检查，但只把会影响 TP 归组、拆分或通过判定的问题作为 S2 重点。不影响 TP 生成与判定的 TC 级细节不属于 S2 检查范围：不进问题清单、不登记、不向用户展示；后续环节如何补充由 S6/S7 按各自检查单与锚点底册覆盖，不是 S2 要考虑的事。

| 维度 | S2 必查：影响 TP 的内容 | 不属于 S2 检查范围：不登记，S6/S7 按检查单与锚点底册覆盖 |
|---|---|---|
| 完整性 | 业务目标、功能范围、参与角色、关键前置条件、结果方向；会改变结果的主要分支；明确的排除项与外部依赖 | 全量测试数据、字段取值枚举、详细边界值、页面文案和布局、接口字段与错误码 |
| 一致性 | 目标功能与关联流程、跨模块规则之间是否冲突；状态、角色、业务对象等关键术语是否同义 | 不影响目标功能行为的文字、格式和非关键命名问题 |
| 无二义性 | 歧义是否会改变业务目标归属、TP 是否拆分、角色/状态处理或通过标准 | 不改变上述内容的展示和实现细节 |
| 可测试性 | 每项业务能力是否有可观察的结果方向，能否判断通过或不通过；是否依赖无法确认的外部条件 | 具体造数方案、字段级组合、精确提示文案；PRD 未给出的性能数值不得自行补写 |
| 可追溯性 | 每项 TP 是否能定位到 PRD 原文、编号或锚点；目标范围和排除范围是否可区分 | 与本次目标功能无关的全篇修订历史整理 |

### S2 一致性检查工作法（矛盾检测矩阵 · 候选态）

一致性维度不得凭印象自由检索。每个维度先按种子词表用检索工具（grep 等）在 PRD 全文定位出现位置，再对命中条目做语义两两比对，比对结论（兼容/冲突/无法判定）留痕。维度清单当前为**候选态**（未经正式基准回归集转正验证），前两个为高置信维度、必须执行，其余按目标功能相关度选用：

| 维度（候选态） | 种子词表示例 | 比对目标 |
|---|---|---|
| 数据可见范围 | 可见/权限/范围/自己创建/项目归属/创建人 | 同一对象的可见判定规则是否唯一 |
| 操作入口与按钮归属 | 按钮/入口/操作区/编辑/复制/删除/只读/无修改 | 目标功能与他功能对同一页面的入口描述是否兼容 |
| 状态流转 | 状态/待审核/已审核/关闭 | 状态枚举与流转规则是否唯一 |
| 角色能力 | 角色/测试人员/测试管理人/管理员/可配置 | 角色与能力分配规则是否唯一 |
| 字段与统计标准 | 字段/取值/统计/来源 | 同一字段的取值来源与统计规则是否唯一 |
| 时间与触发条件 | 触发/定时/实时/当天/时间 | 触发时机与时间标准是否唯一 |
| 校验时机 | 校验/身份/前置/阻止/拦截/权限 | 同一行为的校验时机与条件在各处描述是否唯一（实例：新增风险提交时是否校验审核人身份，前置条件、必填约束、提醒路由、审核权限四处说法不闭合） |

- 检索交给工具（确定性），判读交给 LLM；种子词表与维度清单是本 skill 静态资产，逐次迭代积累。
- 同类横向自查：附录处置完成后，对同属一个页面/同一交互层级的候选（如分页与排序）做处置一致性核对；判定不一致时必须写明实质差异（如「是否产生互斥预期结果」），否则同判。
- 候选态约束：矩阵未捕获的矛盾不视为流程失败；维度转正依赖基准回归集（尚未建立，素材按 baseline/log.md 渐进积累）。

### S2 有意决策判据（防误报三问）

对「PRD 未给出量化标准/细节」的候选问题，先过三问，**三问全部满足则不登记**：

1. PRD 是否明确声明不设硬性指标或有意留白（如「不作为硬指标写入」「待核验」「属 XX 阶段确认」）？
2. PRD 是否给出了验证方式（哪怕主观走查或方向性约束）？
3. 该缺失是否不影响业务级 TP 的归组、拆分或通过判定？

三问不满足、属真缺失且影响 TP 判定的，正常登记。金标准未定的边缘案例，按判据执行并在报告附录标注「金标准未定，按判据暂定」。

### S2 登记前最后一问（防误判收口）

每个候选登记前强制回答最后一问：**该问题是否会产生两种互斥的预期结果，或改变某 TP 的归组、拆分、通过判定？**

- 是 → 登记（冲突改变预期结果，如两条可见范围规则给出不同的展示集合）
- 否 → 不登记（仅枚举/清单/参数类输入不全，不产生第二种预期结果）

**「输入不全类」判别模板**：PRD 写出某能力（如列表「支持部分列排序」「分页展示」）但未给出枚举、清单或参数时，默认属 TC 级细节：不登记；锚点底册保留原文，由 S6/S7 按检查单与覆盖对照覆盖，或列待澄清。仅当该能力整体无任何判定依据（结果方向完全不可判）时才登记。

### S2 歧义处置

- PRD 将条件并列写在同一业务能力下，未说明不同处理时：按 test-point-spec 合并规则**默认合并为一条 TP**，并在问题清单记录歧义；是否该拆分一律按 test-point-spec 切分规则判定，本 skill 不复述。
- 通过标准本身无法从 PRD 或已确认材料确定时：记录待澄清；该行为不得作为已确认 TP 基线，不得自行补造预期。
- PRD 明确写出的字段约束、边界、枚举和异常要求，即使不增加 TP 数量，也必须保留在锚点底册（scope.md）中，由 S6/S7 按材料检查单与覆盖对照确认 TC 覆盖方式；S2 不将其登记为问题。
- **待核验标记消歧**：PRD 的「待核验/待澄清」标记只吸收该条目**自身未定**的部分（如权限矩阵不完整、可编辑字段范围未定）；已写死内容之间的冲突——即在任何待核验结论下都存在的矛盾（如页面按钮存在性两种说法相反）——不得被标记吸收，必须登记。

### S2 漏锚扫描（底册完备性自查）

五维质检完成后、产出 prd-check 报告前执行。目的：防止底册漏建锚点导致系统性漏测——覆盖对照表只能证明「底册内的都验了」，不能证明「底册没漏」。

1. **构造检索词表**：目标功能名称原文 + 所属模块名称 + 底册引用链登记的被引功能名称；禁止自创同义词
2. **检索**：对需求目录 `prd.txt` 快照逐词 `grep -n`；命中行按章节聚合（同章节多命中合并为一处）
3. **逐处三判定**：已建锚（注明锚点）/ 疑似缺锚 / 范围外（一行原因）
4. **落痕与补录**：全部判定写入 prd-check 报告附录「漏锚扫描」表；疑似缺锚项经用户在 S2 门禁一并确认后补录底册（锚点规则 3），state.md 登记补录版本；不新增独立门禁
5. **降级**：快照不可用（锚点规则 9 降级）时本扫描显式声明「未执行，底册完备性未核验」，并在 prd-check 报告登记缺失

### S2 进入 S3 的标准

目标范围内的业务能力均有出处；并列条件已按 TP 规范收拢；需要拆分的不同业务规则已识别；每项候选 TP 都能说明结果方向。不影响 TP 范围和判定的细节不属于 S2 检查范围，不进问题清单；影响通过标准的问题须先待澄清，不能作为已确认基线。

## 问题分级

问题清单只收录影响 TP 生成与判定的问题，仅两级：

- **Blocker**：目标业务能力或通过标准无法确定，无法生成可判定的 TP
- **Major**：可以形成暂定 TP，但未决问题可能改变 TP 范围、拆分或验收结果

不影响 TP 生成与判定的 TC 级细节不是问题，判定标准见上节「S2 PRD 质检范围」。

**问题清单措辞要求**（遵循 test-manager agent 的「表达四原则」，此处只留本报告的场景示例）

- 「问题描述」「对测试的影响」两列按「现状（哪里写了什么）→ 差异/缺失 → 影响」直白句式，一句话说清
- 正例：「两条规则说法不一致：一条说按项目归属判断可见范围，另一条说普通测试人员只能看自己创建的风险」；反例：「两条规则存在口径张力」

## 处置协议

1. 用户澄清/补充说明后：核对受影响问题，更新处置记录；澄清结论由测试经理以 `CL-<序号>` 编号登记于 state.md「挂起/降级」行（逐条 `CL-<序号>：<结论>`，validate.sh state 模式校验编号唯一），后续报告与派发单仅引用 CL 编号 + 关键句，不贴全文；prd-check 处置记录由质检 subagent 写入（复查轮次或下一阶段按派发单补录），TP 依据可写「锚点 + 底册摘录 + CL 编号」（溯源规则见 test-manager 工作铁律 4）
2. PRD 文件变更：本流程暂不支持——指纹比对发现 PRD 原文件变化时按 test-manager 工作铁律 6 暂停并请用户二选一（恢复原 PRD / 挂起功能从 S1 重新开始）
3. Blocker 未清零：声明风险 → 用户以「通过 + 阶段名」二次确认 → state 登记降级决策（强确认协议见 test-manager 工作铁律 2）
