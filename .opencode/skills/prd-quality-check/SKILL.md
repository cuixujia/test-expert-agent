# 需求与证据质检——唯一定义源

**职责边界**：装「需求长什么样才算可测、证据怎么建与引用、PRD 怎么查、报告怎么写」；不装产出核验清单与问题分级（见 self-review-checklist）、资料清单（见 tdd-quality-check）、分析方法（见 test-analysis-methods）。

## 一、锚点规则（编号 1~9，脚本注释按编号引用）

1. **锚点编号生成（编号只来自标题；标题没编号才自建）**——每条内容独立判定：看它归属的 markdown 标题行。

   - **情形 A｜标题带编号**：锚点 = 该条内容**最近的上级标题行**开头的编号，逐字照抄（`## 5. 功能矩阵`→`5`；`### 7.3 可用性要求（适用：F01）`→`7.3`；`#### 4.2.1 余额不足处理（B01）`→`4.2.1`）。就近原则，不跳级、不取别处标题；编号在原文找不到出处→改走情形 B。
   - **情形 B｜标题无编号（或内容不在任何标题下）**：按 `M<模块号>-S<章节号>-P<段落号>` 自建——M=一级标题（`##`）序号，S=二级标题（`###`）序号（无二级标题写 0），P=该节内可独立判定的段落序号（整节不细分写 0）。段落=同层级的加粗小节/事件块/编号列表项，按出现顺序计数。
   - **不是锚点的编号**：标题括号内（`（适用：F01）`）与正文中的编号——事件号 `E01`、分支号 `B01`、规则号 `R01`、功能号 `F01`、存量编码 `FUN…`、外部引用 `BRD 3.1`、系统编码、需求/任务 ID——只能出现在条目摘要与原文摘录里。
   - **锚点就是一个编号，绝不拼接**：`4.3.4-1`、`M5-S0-P0-1`、`7.2-3` 这类「标题号+自造序号」一律不是锚点。同一标题下多条规则**不靠拆编号**——条目摘要分行列明，摘录取一句代表性原文；需分别溯源而 PRD 无更细编号→登记为 S2 澄清项，由用户与需求侧决定。
   - **同一原文位置只能有一个锚点**；不同原文位置不得共用锚点。
   - **形态语法（脚本建册即拦）**：字母/数字/小数点组成 1~4 段、段间 `-`、整串至少含一个数字。合法：`5`、`3.2`、`M5-S0-P3`、`REQ-001`；非法：含中文、无数字纯字母串、编号拼接、小数点后段含字母（`7.2a`）。形态合法 ≠ 可当锚点——`E01`/`F01` 形态合法但会被**来源校验**拦下。
   - **来源校验（脚本机检）**：底册锚点必须整体等于快照中某个标题编号，或严格三段的 M-S-P 自建编号（M/S 须对上标题序号）——不做前缀匹配、不剥后缀。
2. **锚点底册（scope.md，唯一证据底册）**：确定目标功能后通读 PRD，仅为该功能及必要横切依赖建锚；目标功能未定前不得预建全部功能明细锚点；建册后冻结，唯一例外是完备性扫描发现的缺锚经用户确认后受控补录。
3. **粒度**：底册一行 = 一个锚点 = PRD 的一个标题（或一个自建编号），不为区分规则而拆编号。纯背景、元信息、目录类章节不建锚。
4. **原文摘录（模型摘录，不机验）**：≤40 字，从该标题正文中摘取**最能代表规则内容的一句原文**——保持原文文字与标点，不得摘要、改写、跨行拼接；一句完整的原话胜过半句碎片，宁可短一句也不要断句残片。摘录直接写进底册「原文摘录」列（不用任何符号包裹）。摘录的作用是让质检与用户一眼看到依据说了什么——信息量为零的摘录（如只抄标题本身）在质检时按无效依据处理。
5. **去重**：语义重复段落只保留更具体/更权威的一条，其余注明「由 <锚点> 覆盖」；有独有条件或结果的分别保留。
6. **引用链轻登记**：目标功能引用其他功能处（如「编辑在 FUNC-04 定义」）逐项登记到 scope.md「引用链登记」节；仅作检索入口，不参与覆盖对照表。
7. **功能码**：TP/TC 编号的功能码直接取平台 bizFunctionId（功能目录名），仅作编号用途；名称引用一律与 PRD 原文逐字一致。
8. **PRD 文本快照（prd.txt）**：建底册时把权威 PRD 转纯文本落功能目录（`snapshot` 模式，内置引号归一；**禁止模型转写**）。快照只读、已存在即拒绝重建。`.md`/`.txt` 源文件可直接 read 原件；`.docx` 等二进制必须由脚本转换生成快照后再读。内嵌图片等不可解析内容先自行解读（结论标「AI 解读待确认」），无法解读才降级声明；PDF/图片等不可文本化材料在 scope.md 写 `> 快照机验：跳过（<原因>）` 降级。
9. **PRD 版本锁定**：快照与底册建立时登记 PRD 原件 md5；此后 PRD 文件变化 → 暂停，用户二选一（恢复原 PRD / 按新 PRD 重开）；流程内不支持修改 PRD 文件，问题一律靠澄清登记。

## 二、validate-prd.sh 用法

> 读文件不必先跑脚本：read 工具能直接读 `prd.txt`（`.md`/`.txt` 源文件连原件都能读）。脚本只用于生成快照、机验、漏锚扫描与程序化定位。

```bash
V=".opencode/skills/prd-quality-check/validate-prd.sh"
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" snapshot "<PRD 文件名>"   # 生成快照 + 输出源 md5
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/scope.md" scope     # 底册机验（锚点形态+来源）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/scope.md" scan      # 漏锚扫描一键候选
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" find "<关键词>"            # 定位原文行
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" line <行号>               # 取该行原文（含 markdown 符号）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" cat                       # 快照全文带行号
```

- 判读：退出码 0 = 通过；非 0 = 有 FAIL，按报错修复后重跑
- **建底册的标准动作**：① 通读——read 读 `prd.txt`，按章节顺序边读边写锚点行；② 摘录——从已读原文中直接摘取 ≤40 字代表性原句；③ 每批（3~5 行）写完跑一次 `scope` 机验，全部过完后 `scan` 补漏
- 锚点语法与本节规则 1 一致（脚本正则是其实现，改一处必须同步另一处）

**脚本调用规范**：

1. 入参必须是 bash 可见路径——相对仓库根或 WSL 绝对路径（`/mnt/...`）；禁止传 Windows 绝对路径（`D:\...`），中文目录名原样传参，不确定先 `ls` 确认
2. `find` 关键词必须取自快照原文用词；未命中换词或改用 `line`/`scan`，不得原样重试
3. **失败熔断**：同一命令连续失败 2 次→换做法；连续 3 次→停止并报告「脚本/环境问题 + 已试参数 + 实际报错」。**禁止把脚本调用包进 `bash -c '…$变量…'`**——外层 shell 会吃掉 `$`，表现为变量为空、`echo $?` 恒 0 掩盖失败；批量场景把循环写成临时 `.sh` 放 `/tmp` 执行
4. Windows 环境下 shell 输出中文先设 UTF-8（`[Console]::OutputEncoding=[Text.Encoding]::UTF8; $OutputEncoding=[Text.Encoding]::UTF8;`），Linux 无此问题

## 三、scope.md 模板（validate-prd.sh 校验契约）

```markdown
# <目标功能> 锚点底册
（仅当 PRD 不可文本化时保留下一行降级声明）
> 快照机验：跳过（<原因>）

## 锚点清单
| 锚点 | 条目摘要 | 原文摘录 |
|---|---|---|
| 3.2 | 功能范围：产品货架展示、产品详情查看、购买信息录入等 | 在个人网银渠道展示可售的普通定期存款产品列表 |

| 被引功能编号 | 引用事项 | 原文摘录 |
|---|---|---|
```

## 四、PRD 质检（以「足以定义测试点」为准，不追求可写全部 TC）

**目的**：确认需求文档足以支撑「有证据、范围清楚、结果可判定」的业务级 TP。不影响 TP 归组、拆分或判定的 TC 级细节（字段枚举、精确文案、错误码等）不属于检查范围：不登记、不上报。

| 维度 | 必查：影响 TP 的内容 | 不查：TC 级细节 |
|---|---|---|
| 完整性 | 业务目标、功能范围、角色、关键前置、结果方向、主要分支、排除项与外部依赖 | 全量测试数据、字段取值枚举、详细边界值、页面文案布局 |
| 一致性 | 与关联流程/跨模块规则冲突；关键术语同义性 | 不影响行为的文字格式问题 |
| 无二义性 | 歧义改变目标归属、拆分或通过标准 | 展示实现细节 |
| 可测试性 | 每项能力有可观察结果方向；无不可确认的外部依赖 | 造数方案、字段组合、精确文案 |
| 可追溯性 | 每项 TP 可定位到原文；目标/排除范围可区分 | 无关的修订历史整理 |

### 矛盾检测（检索交给工具，判定交给 LLM）

先按种子词表用检索工具在 PRD 全文定位，再对命中条目做语义比对。维度清单为**候选态**，前两个必须执行，其余按相关度选用：

| 维度（候选态） | 种子词示例 | 比对目标 |
|---|---|---|
| 数据可见范围 | 可见/权限/范围/自己创建/创建人 | 同一对象的可见判定规则是否唯一 |
| 操作入口与按钮归属 | 按钮/入口/编辑/复制/删除/只读 | 目标功能与他功能对同一页面的入口描述是否兼容 |
| 状态流转 | 状态/待审核/已审核/关闭 | 状态枚举与流转规则是否唯一 |
| 角色能力 | 角色/测试人员/管理员/可配置 | 角色与能力分配规则是否唯一 |
| 字段与统计标准 | 字段/取值/统计/来源 | 同一字段的取值来源与统计规则是否唯一 |
| 时间与触发条件 | 触发/定时/实时/当天 | 触发时机与时间标准是否唯一 |
| 校验时机 | 校验/身份/前置/阻止/拦截/权限 | 同一行为的校验时机与条件在各处描述是否唯一 |

- 种子词表与维度清单是本 skill 静态资产，逐次迭代积累；矩阵未捕获的矛盾不视为流程失败
- **同类横向自查**：对同属一个页面/交互层级的候选做处置一致性核对；判定不一致必须写明实质差异，否则同判

### 防误报两道闸

- **有意决策三问**（对「PRD 未给量化标准/细节」的候选）：①PRD 声明有意留白？②给了验证方式（哪怕主观走查）？③不影响 TP 归组/拆分/判定？三问全满足→不登记
- **登记前最后一问**：该问题会产生两种互斥预期结果，或改变 TP 的归组/拆分/通过判定？否→不登记。「输入不全」默认属 TC 级细节不登记
- **待核验标记消歧**：「待核验」只吸收该条目自身未定部分；已写死内容之间的冲突必须登记

### 歧义处置

- 并列条件未说明是否区别处理→按 test-point-spec 合并规则默认合并，歧义记入问题清单
- 通过标准无法确定→记待澄清，不得自行补造预期
- PRD 明确的字段约束、边界、枚举、异常即使不增 TP 数量也必须建锚进底册；本环节不将其登记为问题

### 完备性扫描（防底册漏锚）

五维质检后、出报告前执行 `scan` 一次产出章节锚点覆盖状态与功能名命中行；**只对「疑似缺锚候选/无编号/部分覆盖」行做三判定**（已建锚/疑似缺锚/范围外）；疑似缺锚列待用户确认后补录底册。检索词只允许「目标功能名称原文+所属模块名称+底册引用链登记的被引功能名称」，禁止自创同义词。快照不可用时本扫描显式声明「未执行」。

### 进入测试点生成的准入标准

目标范围内的业务能力均有出处；并列条件已按 TP 规范收拢；需要拆分的不同业务规则已识别；每项候选 TP 都能说明结果方向。影响通过标准的问题须先待澄清，不能作为已确认基线。

## 五、可选资料登记

- 资料清单、必需性与缺失处理见 tdd-quality-check「资料输入模型」，本 skill 不重述
- PRD 质检时登记测试点生成可用的可选资料（领域知识、逆向文档、功能知识、存量测试点）：路径、提供情况、可读性与相关性
- 可选资料与 PRD 冲突→以 PRD 为准；若冲突改变 TP 范围/拆分/通过标准，按输入问题暂停请用户澄清
- 存量测试点仅作参考，不是本次基线，不得整批复制

## 六、问题分级

**级别与处置方定义见 self-review-checklist**（唯一权威源），本环节只规定判定口径：

- **Blocker**：目标业务能力或通过标准无法确定，无法生成可判定的 TP
- **Major**：可形成暂定 TP，但未决问题可能改变范围、拆分或验收结果
- 只登记影响 TP 定义与判定的问题；TC 级细节不是问题，不登记、不向用户展示

## 八、处置协议与澄清登记（CL）

1. **用户澄清/补充说明后**：核对受影响问题并更新处置记录；澄清结论由流程编排方以 `CL-<序号>` 登记 state.md「澄清登记」登记项（编号只增、只在该登记项内定义，其他字段一律引用编号；落点定义见 test-manager），后续报告与派发只引用 `CL 编号 + 一句话关键结论`。用户澄清结论可作为 TP 依据，注明 CL 编号
2. **PRD 文件变更**：不支持修改 PRD 文件——指纹比对发现原件变化时按规则 9 版本锁定处理（暂停，用户二选一）
3. **Blocker 未清零**：声明风险→用户以「通过 + 阶段名」二次确认→风险决策登记状态文件（强确认协议由流程编排方执行）
