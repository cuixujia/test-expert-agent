# 需求与证据质检——唯一定义源

**职责边界**：装「需求长什么样才算可测、证据怎么建与引用、PRD 怎么查、报告怎么写」；不装产出核验清单与问题分级（见 self-review-checklist）、资料清单（见 tdd-quality-check）、分析方法（见 test-analysis-methods）。

## 锚点（证据）规则

锚点是 PRD 原文的定位标记，是「所有测试内容必须可回查需求原文」的证据链基础。

1. **锚点编号生成（编号只来自标题；标题没编号才自建）**

   **判定顺序（每条内容独立判定）**：先看该条内容归属的 markdown 标题行——标题带编号走「情形 A」；标题不带编号（或该内容位于任何标题之外的无标题段落）走「情形 B」。

   - **情形 A｜所在标题带编号 → 取标题编号**
     - 锚点 = **该条内容最近的上级标题行开头的编号**，逐字照抄，不加不减：`## 5. 功能矩阵` → `5`；`### 7.3 可用性要求（适用：F01）` → `7.3`；`#### 4.2.1 余额不足处理（B01）` → `4.2.1`；`#### 6.1.1 F01 定期存款购买` → `6.1.1`。
     - **就近原则**：一条内容归属哪个标题，就用那个标题的编号——不得跳级取更上层标题，也不得取别处标题的编号。
     - **编号必须真实存在于 PRD**：锚点里的编号在原文找不到出处 → 不是锚点，改走情形 B 自建。
     - **标题括号内、标题中间的编号不是锚点**：`（适用：F01）`、`（B01）`、`6.1.1 F01 定期存款购买` 中的 `F01`/`B01` 一律不进锚点。
     - **正文中的编号一律不是锚点**：流程事件号（`E01`…）、分支事件号（`B01`…）、规则号（`R01`…）、对象码（`O01`…）、功能号（`F01`…）、存量功能编码（`FUN…`）、外部文档引用号（`BRD 3.1`）、系统编码、需求/任务 ID —— 这些只能出现在「条目摘要」与「原文摘录」里，不得当锚点。
   - **情形 B｜所在标题不带编号（或内容不在任何编号标题下）→ 按规则自建编号**
     - 按 `M<模块号>-S<章节号>-P<段落号>` 派生：`M` = 所属一级标题（`##`）序号、`S` = 所属二级标题（`###`）序号（该一级标题下无二级标题时写 `0`）、`P` = 该节内可独立判定的**段落**序号（从 1 起；整节不作细分时写 `0`）。
     - 段落 = 该节内同层级的加粗小节/事件块/编号列表项，按出现顺序计数（`## 5. 功能矩阵` 下：功能子步骤说明=1、变化类型说明=2、完全复用子步骤=3、调整子步骤=4、表外复用说明=5）。
     - 例：「完全复用子步骤」→ `M5-S0-P3`（其下第 1 条列表项并入本锚点，不另编号）。
   - **锚点就是一个编号，绝不拼接**：锚点只能是**一个**编号——要么 PRD 里的标题编号（原样照抄，如 `7.3`、`4.2.1`、`6.1.1`），要么自建的 `M-S-P`（如 `M5-S0-P3`）。**禁止把编号拼在一起**：`4.1-4-2`、`4.3.4-1`、`M5-S0-P0-1`、`7.2-3` 这类「标题号 + 自造序号」一律不是锚点。
   - **同一标题下有多条可独立判定的规则怎么办**：**不靠拆编号解决**——底册一行 = 一个锚点 = PRD 的一个标题，条目摘要中把该标题下的多条规则**分行列明**，原文摘录取该节的一句代表性原文（≤40 字）。若这些规则需要分别溯源、而 PRD 本身没有更细的编号 → 登记为 S2 澄清项（PRD 是否补编号/拆章节），由用户与需求侧决定，**agent 不得自造编号拼接**。
   - **同一原文位置只能有一个锚点**；不同原文位置不得共用一个锚点（与规则 3 粒度要求同源）。
   - **锚点形态语法（validate-prd.sh scope 模式建册即拦）**：由字母、数字、小数点组成 1~4 段，段间用 `-` 连接，整串至少含一个数字。
     - 合法（PRD 标题编号，原样照抄）：`5`、`3.2`、`3.2.1`、`4.2.1`、`6.1.1`、`7.3`；PRD 标题编号本身是字母数字混排时同样照抄：`E01`、`REQ-001`
     - 合法（自建编号，严格三段）：`M1-S7-P0`、`M1-S2-P3`、`M5-S0-P3`、`M6-S1-P1`
     - 非法：含中文（`表外复用`、`F01-待澄清`、`6.1.1-完成标准1`）、无数字纯字母串（`ABCD`）、**编号拼接**（`4.3.4-1`、`7.2-3`、`M5-S0-P0-1`、`F01-E04`、`M4-S4.1-E07-P1`）、小数点后的段含字母（`7.2a`、`4.3.4a`——小数点后各段只能是纯数字）
     - 注意：形态合法 ≠ 可以当锚点。`E01`、`F01`、`FUN…` 形态合法但不是标题编号也不是自建编号，会被**来源校验**拦下；形态门禁只管写法，来源门禁只管出处。
   - **锚点来源校验（脚本机检）**：底册锚点必须**整体等于**快照中的某个**标题编号**，或是严格三段的 M-S-P 自建编号（`M` 须对上一级标题序号，`S` 须对上二级标题序号，一级标题下无二级标题时才允许 `S0`）——**不做前缀匹配、不剥后缀**，凡带拼接后缀的一律判 FAIL。派生编号是唯一允许的自建来源。
2. **锚点底册（scope.md，唯一证据底册）**：确定目标功能后，通读 PRD，仅为该功能及必要横切依赖建锚；**目标功能未确定前不得为所有功能预建明细锚点**；建册后冻结，唯一例外是完备性扫描发现的缺锚经用户确认后受控补录（登记补录版本）
3. **粒度**：底册一行 = 一个锚点 = PRD 的一个标题（或一个自建编号），**不为区分规则而拆编号**。一个标题下含多条可独立判定的硬规则时：条目摘要中**分行列明**这些规则（可多行），原文摘录取该节的一句代表性原文（≤40 字）。需要分别溯源而 PRD 未给更细编号的，登记为 S2 澄清项（PRD 是否补编号/拆章节），**由用户与需求侧决定，agent 不得自造拼接编号**。纯背景、元信息、目录类章节不建锚
4. **摘录（逐字节抄原文，不是写摘要）**：≤40 字、**必须是 `prd.txt` 快照中连续原文的逐字符复制**——禁止摘要、改写、去标点、补标点、跨行拼接；markdown 语法符号（`#`、`-`、`*`、`|`、反引号、表格竖线）**原样保留**，底册存的是「原文 + 原文符号」而不是读起来通顺的句子。摘录一律用 `「」` 包裹（脚本剥壳后逐字比对，壳不计入 40 字）。TP 引用锚点必须附摘录，防幻觉依据。对话默认只呈现决策所需的功能范围与锚点摘要，不粘贴完整底册
   - **两种读法，别混用（防"逐行翻页"死循环）**：
     - **通读（整体了解 PRD、建册前浏览）** → **首选 `read` 工具一次读完 `prd.txt` 快照**（纯文本，一次到位；`.md`/`.txt` 源文件更可直接 read 原件）；需要分段时用脚本 `cat`（全文带行号）或 `line <起始> <结束>`（区间）。**禁止逐行调用 `line` 翻页**——566 行 PRD 会产生 500+ 次脚本调用，必然卡死；同一模式连续调用超过 10 次即视为用法错误，必须换成批量读法。
     - **抄录（写某一条的摘录）** → 摘录必须逐字符来自原文，两条路等价，**任选其一**：① `read` 工具输出里的原文（快照 `prd.txt` 与原文逐字一致，读到哪抄到哪）；② 脚本 `find <关键词>` 定位 → `line <行号>` 取回 → 复制；底册已有锚点时 `pull <锚点>` 直接取。**禁止凭记忆或摘要改写摘录**（必然导致「摘录未逐字命中快照」）。
   - **脚本是便利工具，不是读文件的前置条件**：`read` 工具能直接读 `prd.txt`（以及 `.md`/`.txt` 原件），就不必先跑脚本取原文。脚本只在三种情况下必须用：① 生成快照（docx 等不可直接读格式的转换与引号归一）；② 逐字机验（`scope`/`pull`）；③ 需要程序化定位与批量提取（`find`/`line`/`cat`）。
   - **抄写后立即机验**：每写完一批锚点就跑 `scope` 机验，不通过时按报错回显的候选原文行重抄，不要自己猜原文。
   - **长度前置检查**：复制后先数字数（≤40 字，含底册行），超长当场截短到同段连续原句重抄；超长不得靠删标点或改写压缩。
5. **去重**：语义重复段落只保留更具体/更权威的一条，其余注明「由 <锚点> 覆盖」；有独有条件或结果的分别保留
6. **引用链轻登记**：目标功能引用其他功能处（如「编辑在 FUNC-04 定义」）逐项登记到 scope.md 的「引用链登记」节：锚点=被引功能编号、条目摘要=引用事项、原文摘录=引用处原句（≤40 字）；仅作检索入口，不展开被引功能全文。**引用链条目不进入「锚点清单」，因此不参与覆盖对照表与摘录机验**
7. **功能码**：TP/TC 编号的功能码直接取平台 bizFunctionId（功能目录名），仅作编号用途，不替代名称；名称引用一律与 PRD 原文逐字一致，禁止缩写改写
8. **PRD 文本快照（prd.txt）**：建底册时把权威 PRD 转纯文本落功能目录（推荐 `bash .opencode/skills/prd-quality-check/validate-prd.sh "<功能目录>" snapshot "<PRD 文件名>"`，内置引号归一；**禁止模型转写**）。快照只读、已存在即拒绝重建；归一后字符是全链路唯一基准。**快照源文件为 PRD 原件**：功能目录 `prd-doc/` 下保留原文件名的原件或软链接，多版本时以用户指定为准。**读法按源文件形态分档**：`.md`/`.txt` 源文件 → `read` 工具可直接读原件与快照，不需脚本参与；`.docx` 等二进制格式 → read 读不出正文，必须由脚本转换（textutil/pandoc）+ 引号归一生成快照后再读快照。内嵌图片等不可解析内容**先自行解读**（解包 docx 提取图片并读图，结论以「AI 解读待确认」标注登入底册或状态文件），无法解读才降级声明并交用户确认；PDF/图片等不可文本化材料在 scope.md 写 `> 快照机验：跳过（<原因>）` 降级
9. **PRD 版本锁定**：快照与底册建立时登记 PRD 原件 md5；此后 PRD 文件变化 → 暂停，用户二选一（恢复原 PRD / 按新 PRD 重开）；流程内不支持修改 PRD 文件，问题一律靠澄清登记

### validate-prd.sh 用法（需求与证据侧硬校验 + 便利提取工具）

> **读文件不必先跑脚本**：`read` 工具能直接读 `prd.txt`（`.md`/`.txt` 源文件连原件都能直接读）。脚本只在「生成快照 / 逐字机验 / 程序化定位与批量提取」时才需要。以下命令用于这三类场景。

```bash
V=".opencode/skills/prd-quality-check/validate-prd.sh"
# 生成 PRD 文本快照（textutil/pandoc + 引号归一 + 输出源文件 md5；只读，已存在即拒绝重建）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" snapshot "<PRD 文件名>"
# 锚点底册校验（三道门禁：锚点形态 + 锚点来源（标题编号/自建编号）+ 摘录逐字命中快照与长度）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/scope.md" scope
# 摘录程序化提取（先自验命中快照再输出；禁止模型手抄）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/scope.md" pull "<锚点>"
# 漏锚扫描一键候选（章节锚点覆盖状态 + 功能名命中聚合）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>/<uuid>/scope.md" scan
# 定位快照原文行（行号 + 原文），建底册抄摘录用
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" find "<关键词>"
# 取回快照某一行的完整原文（含 markdown 标记/列表符号/表格竖线）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" line <行号>
# 取回快照一段行区间（通读用，禁止逐行翻页）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" line <起始> <结束>
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" line <起始>-<结束>
# 一次输出快照全文（带行号，通读用；也可直接用 read 工具读 prd.txt）
bash "$V" "workspace/runtime_<项目>/file/<bizFunctionId>" cat
```

- 判读：退出码 0 = 通过；非 0 = 有 FAIL，必须修复后重跑
- **建底册的标准动作**：① 通读——`read` 工具读 `prd.txt`（或 `cat` / `line <起> <止>` 批量取），按章节顺序边读边起草；② 抄录——`find` 定位 → `line` 取原文 → 逐字符复制到摘录列；③ 每批写完立刻跑 `scope` 机验，不通过时按报错回显的候选原文行重抄
- 锚点语法与本 skill 锚点规则 1 一致（脚本正则是其实现，改一处必须同步另一处）

### 脚本调用规范（Windows 环境，踩坑必读）

1. **入参路径必须是 bash 可见的路径**——相对仓库根（`workspace/runtime_<项目>/file/<bizFunctionId>`）或 WSL 绝对路径（`/mnt/host/d/Project/<项目>/...`）。
   **禁止把 Windows 绝对路径（`D:\...`）传给 bash**：bash 看不见该路径，脚本只会回一行用法，调用方拿不到有效诊断，最容易陷入「同一命令反复重试」。Windows 绝对路径只用于文件读写类工具（read/write/edit）。
2. **中文目录名原样传参**（如 `runtime_个人存款`），不要转义、不要截断、不要替换成猜测的项目名；路径里的每个目录都必须真实存在——不确定就先 `ls` 确认，禁止凭印象拼路径。
3. **`find` 的关键词必须取自 PRD 快照原文用词**，禁止凭印象改写（如快照写「展示可售产品列表」，就不要写成「展示在售产品列表」）；关键词无命中时脚本会明确报「关键词未命中快照」，此时换一个快照里真实出现的词，或改用 `line <行号>` / `scan`，**不得原样重试**。
4. **失败熔断（强制）**：同一条命令连续失败 2 次且没有新信息 → 必须换一种做法（换路径写法 / 换关键词 / 换模式 / 先 `ls` 确认路径）；连续 3 次 → 停止重试，按「异常兜底」向用户报告「脚本/环境问题 + 已试参数 + 实际报错」，并把结论登记状态文件。禁止把同一条命令原样再跑。

### scope.md 模板（validate-prd.sh 校验契约）

```markdown
# <目标功能> 锚点底册
（仅当 PRD 不可文本化时保留下一行降级声明）
> 快照机验：跳过（<原因>）

## 锚点清单
| 锚点 | 条目摘要 | 原文摘录 |
|---|---|---|

## 引用链登记（可选，仅登记目标功能对其他功能的引用；不参与覆盖对照表与摘录机验）

|---|---|---|
```

## PRD 质检（以「足以定义测试点」为准，不追求可写全部 TC）

**目的**：确认需求文档足以支撑「有证据、范围清楚、结果可判定」的业务级 TP。不影响 TP 归组、拆分或判定的 TC 级细节（字段枚举、精确文案、错误码等）**不属于检查范围**：不登记、不上报，由后续环节按各自的检查单覆盖。

| 维度 | 必查：影响 TP 的内容 | 不查：TC 级细节 |
|---|---|---|
| 完整性 | 业务目标、功能范围、角色、关键前置、结果方向、主要分支、排除项与外部依赖 | 全量测试数据、字段取值枚举、详细边界值、页面文案布局 |
| 一致性 | 与关联流程/跨模块规则冲突；关键术语同义性 | 不影响行为的文字格式问题 |
| 无二义性 | 歧义改变目标归属、拆分或通过标准 | 展示实现细节 |
| 可测试性 | 每项能力有可观察结果方向；无不可确认的外部依赖 | 造数方案、字段组合、精确文案 |
| 可追溯性 | 每项 TP 可定位到原文；目标/排除范围可区分 | 无关的修订历史整理 |

### 矛盾检测（检索交给工具，判定交给 LLM）

先按种子词表用检索工具在 PRD 全文定位，再对命中条目做语义比对，结论留痕。种子维度清单为**候选态**（未经正式基准回归集转正验证），前两个为高置信维度、必须执行，其余按目标功能相关度选用：

| 维度（候选态） | 种子词表示例 | 比对目标 |
|---|---|---|
| 数据可见范围 | 可见/权限/范围/自己创建/项目归属/创建人 | 同一对象的可见判定规则是否唯一 |
| 操作入口与按钮归属 | 按钮/入口/操作区/编辑/复制/删除/只读/无修改 | 目标功能与他功能对同一页面的入口描述是否兼容 |
| 状态流转 | 状态/待审核/已审核/关闭 | 状态枚举与流转规则是否唯一 |
| 角色能力 | 角色/测试人员/测试管理人/管理员/可配置 | 角色与能力分配规则是否唯一 |
| 字段与统计标准 | 字段/取值/统计/来源 | 同一字段的取值来源与统计规则是否唯一 |
| 时间与触发条件 | 触发/定时/实时/当天/时间 | 触发时机与时间标准是否唯一 |
| 校验时机 | 校验/身份/前置/阻止/拦截/权限 | 同一行为的校验时机与条件在各处描述是否唯一（实例：新增风险提交时是否校验审核人身份，前置条件、必填约束、提醒路由、审核权限四处说法不闭合） |

- 检索交给工具（确定性），判读交给 LLM；种子词表与维度清单是本 skill 静态资产，逐次迭代积累
- **同类横向自查**：附录处置完成后，对同属一个页面/同一交互层级的候选（如分页与排序）做处置一致性核对；判定不一致时必须写明实质差异（如「是否产生互斥预期结果」），否则同判
- 候选态约束：矩阵未捕获的矛盾不视为流程失败；维度转正依赖基准回归集（尚未建立，素材按 baseline/log.md 渐进积累）

### 防误报两道闸

- **有意决策三问**（对「PRD 未给量化标准/细节」的候选）：①PRD 声明有意留白（如「不作为硬指标写入」「待核验」）？②给了验证方式（哪怕主观走查）？③不影响 TP 归组/拆分/判定？三问全满足 → 不登记
- **登记前最后一问**：该问题会产生两种互斥预期结果，或改变 TP 的归组/拆分/通过判定？否 → 不登记。「输入不全」默认属 TC 级细节不登记，仅当该能力整体无任何判定依据才登记
- **待核验标记消歧**：PRD「待核验」只吸收该条目自身未定部分（权限矩阵不完整、可编辑字段范围未定）；已写死内容之间的冲突（任何待核验结论下都存在的矛盾，如按钮存在性两种说法相反）必须登记

### 歧义处置

- 并列条件未说明是否区别处理 → 按 test-point-spec 合并规则默认合并，歧义记入问题清单
- 通过标准无法确定 → 记待澄清，不得自行补造预期
- PRD 明确的字段约束、边界、枚举、异常，即使不增 TP 数量，也必须建锚进底册，由后续环节按检查单与覆盖对照确认覆盖方式；本环节不将其登记为问题

### 完备性扫描（防底册漏锚）

五维质检后、出报告前执行：`bash "<路径>/validate-prd.sh" "<会话目录>/scope.md" scan` 一次产出章节锚点覆盖状态与功能名命中行；**只对「疑似缺锚候选/无编号/部分覆盖」行做三判定**（已建锚/疑似缺锚/范围外）；疑似缺锚列待用户确认后补录底册。禁止逐词 grep 循环。

- **检索词表约束**：只允许「目标功能名称原文 + 所属模块名称 + 底册引用链登记的被引功能名称」，**禁止自创同义词**扩充检索面
- **降级声明**：快照不可用（规则 8 降级）时本扫描显式声明「未执行，底册完备性未核验」，并在报告登记缺失

### 进入测试点生成的准入标准

目标范围内的业务能力均有出处；并列条件已按 TP 规范收拢；需要拆分的不同业务规则已识别；每项候选 TP 都能说明结果方向。不影响 TP 范围和判定的细节不进问题清单；影响通过标准的问题须先待澄清，不能作为已确认基线。

## 可选资料登记

- **资料清单、目录位置、必需性与缺失处理见 tdd-quality-check「资料输入模型」**，本 skill 不重述
- PRD 质检时登记测试点生成可用的可选资料（领域知识、逆向文档、功能知识、存量测试点）：记录路径、提供情况、可读性与相关性；不对可选资料另做一轮完整 PRD 质检
- 可选资料与 PRD 冲突 → **以 PRD 为准**；若冲突会改变 TP 范围、拆分或通过标准，按输入问题暂停并请用户澄清
- 存量测试点仅作参考，不是本次基线，不得整批复制（使用规则见 test-point-spec）

## 问题分级

**级别与处置方的定义见 self-review-checklist**（唯一权威源），本环节只规定判定口径：

- **Blocker**：目标业务能力或通过标准无法确定，无法生成可判定的 TP
- **Major**：可形成暂定 TP，但未决问题可能改变范围、拆分或验收结果
- 只登记影响 TP 定义与判定的问题；不影响 TP 生成与判定的 TC 级细节不是问题，不登记、不向用户展示

## 处置协议

1. **用户澄清/补充说明后**：核对受影响问题并更新处置记录；澄清结论由流程编排方以 `CL-<序号>` 登记状态文件（编号唯一，编号唯一性由 `self-review-checklist/validate.sh` state 模式校验），后续报告与派发只引用 `CL 编号 + 一句话关键结论`；用户澄清结论可作为 TP 依据，注明 CL 编号
2. **PRD 文件变更**：本流程不支持修改 PRD 文件——指纹比对发现原件变化时按锚点规则 9 版本锁定处理（暂停，用户二选一：恢复原 PRD / 按新 PRD 重开）
3. **Blocker 未清零**：声明风险 → 用户以「通过 + 阶段名」二次确认 → 风险决策登记状态文件（强确认协议由流程编排方执行）
