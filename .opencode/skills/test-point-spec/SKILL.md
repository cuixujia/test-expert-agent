# 测试点（TP）规范——唯一定义源

**职责边界**：装「测试点是什么、怎么切、怎么写、怎么编号、怎么改」；不装用例规范（见 test-case-spec）、资料清单（见 tdd-quality-check）、核验清单与问题分级（见 self-review-checklist）、分析方法（见 test-analysis-methods）。

## 定义

**测试点（TP）= 一项可判定通过或不通过的业务验证目标。**说明验证哪项业务能力、结果应符合什么方向。测试数据、操作步骤、具体预期文案归测试用例（TC）。

- TP 不按字段、输入值、角色或控件逐项拆分；这些维度由关联 TC 覆盖
- TP 数量不作为目标：不为少而漏规则，不为多而拆碎

## 一条 TP 必须同时满足三条（缺一不许出）

### 一 · 说得出出处（证据）

- **PRD 写了的**：挂锚点（PRD 原文定位标记，建册规则见 prd-quality-check）+ ≤40 字原文摘录（从 PRD 原文摘取代表性原句，忠实原文、不得摘要改写）。验证的事必须就是这句话说的事，不许拿一句话当幌子验它没说的内容
- **PRD 没写、但必须验的**：注明推导来源（流程推的/状态推的/行业惯例推的），挂最相关原文，且不与 PRD 明文矛盾
- 两条都占不住 → 无依据，禁止产出

### 二 · 切得不多不少（按业务能力切，不按字段切）

- **该合**：PRD 将多个条件并列在同一业务能力下、且未规定不同流程/规则/权限/结果 → 合成一条，即使某项可能单独出错（由 TC 单独覆盖）
- **该拆**（仅三种）：不同业务目标 / PRD 明文规定不同流程、规则、权限或结果 / 主副项验收要求不同
- **描述不清**：默认合并，模糊点记入质检报告问题清单；通过标准定不出来 → 标待澄清，不得充当已确认基线
- 三违规：**太大**（多条不同规则塞一条）/ **太小**（同一套处理的不同数据拆多条）/ **耦合**（明细验证与能力验证重复）

### 三 · 判得了对错

写完必须能回答：「真执行了，看什么能分出过/不过？」答不上来就别出。通过判定口径：所含 PRD 要求全部满足才通过，任一不满足即不通过；各 TC 结果分别记录。

## 命名

「验证」+ 对象 + 结果方向，≤30 字：

- 对象**直抄 PRD 原词**，不自创同义词（名称是用例库检索键）
- 禁止：具体提示文案/错误码/账务变化等预期细节、操作步骤、功能描述（「系统能 XX」不是 TP）

| 示例 | 判定 |
|---|---|
| 验证超单笔限额的转账被拒绝 | ✅ 一条逻辑、一个结果方向、PRD 原词 |
| 验证高级搜索按支持条件筛选风险 | ✅ 同一搜索能力下的多项并列条件合并为一条，各条件由 TC 覆盖 |
| 验证详情信息完整展示 | ✅ 同一完整性要求下的多个字段合并，字段清单由 TC 核对 |
| 验证转账功能正确 | ❌ 多条规则塞一条，没法判 |
| 验证输入 0 元和负数均被拒绝 | ❌ 同一套处理，具体数据是用例的事 |

## 编号通用约定（TP 与 TC 共用）

- **功能码**：直接取平台 `bizFunctionId`（即功能目录名），仅作编号用途，**不替代名称**；确定后全流程不变，不另设注册表
- **序号**：三位起、只增不改不复用；删除只标记废弃
- **名称一致性**：一切产出（清单标题与正文、对话输出）引用的业务模块名与功能名，必须与 PRD 原文逐字一致（含模块编号/功能编号），禁止缩写、简写、改写
- **产物状态字样**：草稿 / 质检后 / 已验收（测试用例为 草稿 / 质检后 / 已评审），由流程编排方在产物标题行标注

## 字段规范

| 字段 | 要求 |
|---|---|
| 编号 | `TP-<功能码>-NNN`（编号通用约定见上节） |
| 验证意图 | 按命名格式，能独立判断对错 |
| 类型 | 功能 / 异常 / 边界 / 流程 / 非功能（单选；非功能仅 PRD 提及或高风险时生成） |
| 分析方法 | 等价类/边界值/判定表/场景法/状态迁移/正交实验/因果图/错误推测（选用规则见 test-analysis-methods） |
| 依据 | 格式 `锚点；摘录`（多个锚点用 `、` 连接；锚点在前、摘录在后，validate.sh 按此提取锚点）；摘录为 ≤40 字原文摘录，从 PRD 原文摘取代表性原句；推导项注明来源；禁止无依据 TP |

## 清单模板（列序为校验契约，禁止调整）

```markdown
# <目标功能> 测试点清单（状态：草稿 / 质检后 / 已验收）

| 编号 | 验证意图 | 类型 | 分析方法 | 依据（锚点；摘录） |
|---|---|---|---|---|

## 覆盖对照表（以 scope.md 锚点底册为准）
| PRD 锚点 | 覆盖的 TP 编号 | 未覆盖原因 |
|---|---|---|
（每个底册锚点必须出现在本表；未覆盖项填原因、禁止留空）
```

## 边界：TP 不是什么

- **不是功能描述**：功能点=「系统能做什么」，TP=「验证什么」；每个末层功能点必须有 TP，空功能点违规
- **不是测试用例**：TP 不带步骤、数据、具体预期文案；TP:TC = 1:N，一条 TP 至少派生一条 TC，一条 TC 只挂一条 TP
- **覆盖不能有缺口**：功能（正常/异常/边界）+ 界面/兼容/安全/性能 + 领域检查单（见 test-analysis-methods）全维度扫描；非功能型 TP 仅 PRD 提及或高风险时生成

## 质检与校验

TP 核验的两关分工（语义关/形式关）、问题分级与处置方、逐项核验清单与校验脚本用法，**唯一权威源为 self-review-checklist**，本 skill 不复述。

## 排序与基线

- TP 排列顺序 = 依据锚点在 PRD 中的出现顺序
- 验收通过的清单即**基线**：此后只有受控变更（失效/新增/修改），编号只增不改不复用，禁止无差别重生成；删除仅标记废弃

## 变更规则

- 验收确认后的调整 → 修订对应行并重新质检（经修复循环后重新确认）
- **设计材料变更 → 受影响 TP 标记失效，失效 TP 禁止派生 TC**；受影响 TP 重做并重新质检（材料变更协议由流程编排方约定）
- 用户澄清 PRD「没说清」的问题 → 按切分规则重新合并/拆分受影响 TP，并重新质检
- TP 基线错误经用户确认调整 → 回退到生成环节受控变更，编号只增不改不复用，删除仅标记废弃

## 输入与历史测试点使用规则

- **输入资料（必需/可选、目录位置、缺失与冲突处理）见 tdd-quality-check「资料输入模型」**，本 skill 不重述；生成测试点时必须取到：PRD 原件与快照、锚点底册、PRD 质检报告与已登记澄清（CL 编号+关键句）
- 产物写入功能目录 `output/test-point/test-point.md`；具体路径以派发单为准
- **存量测试点使用规则**：仅作覆盖维度与写法参考，**禁止整批拷贝**；每条 TP 仍须独立满足三条硬标准并挂锚点，与 PRD 冲突以 PRD 为准
- 由领域知识、逆向文档、功能知识或历史经验补充的「PRD 没写、推出来」验证目标，按「说得出出处」第二条处理（注明来源，不与 PRD 明文矛盾）
