# 测试用例（TC）规范——唯一定义源

## 定义

**测试用例（TC）= 一条含完整执行信息（前置条件、测试数据、操作步骤、预期结果）的可执行验证，一条用例只验证一个目的。**
- 可执行：执行者无需追问即可照做
- 与 TP 的关系：TC 必须且只能关联一个 TP；一个 TP 至少派生一条 TC

## 字段规范

| 字段 | 要求 |
|---|---|
| 编号 | `TC-<功能码>-NNN`，功能码=平台 bizFunctionId（编号用途，不替代名称）；三位序号只增不改不复用 |
| 标题 | 「场景 + 预期」结构，如「金额超单笔限额，交易拒绝并提示」 |
| 关联 TP | 单个 TP 编号（一对一关联，禁止多值） |
| 优先级 | P0 核心主流程 / P1 重要分支与边界 / P2 次要场景 / P3 罕见与健壮性 |
| 前置条件 | 可构造的具体状态（账户、数据、权限），禁止"系统正常"类空话；环境/版本要求（如 SIT、已配置参数）属前置条件，不单列字段 |
| 测试数据 | 具体值或可执行构造方法，金额/字段给到具体数值 |
| 操作步骤 | 操作者视角，动词开头，编号分步，无歧义词 |
| 预期结果 | 可观察、可判定的结果（界面提示/账务变动/响应码/数据落库），多结果分点列出 |
| 用例类型 | 正向 / 反向 / 边界 / 异常 / 流程（归类判据与优先序见质量标准） |
| 变更状态 | **预留字段，当前流程生成时一律留空**（validate.sh 不校验空值；由 S8 语义质检核对留空） |

## 质量标准

- 一条用例一个验证目的，即**一个 pass/fail 结论**：验证「金额超限拒绝」的用例不得同时断言手续费计算；预期结果可有多个观察点（如「余额不变 + 流水生成」），但必须同属一次判定，出现第二种判定即拆分
- 用例类型归类判据：边界=取值在分区边缘（恰等于/恰超出）；异常=系统或环境故障（超时/断网/脏数据）；反向=操作者合法但违反业务规则被拒；流程=跨页面/跨系统的多步骤业务旅程；正向=其余正常场景；交叉时按 **边界 > 异常 > 反向 > 流程 > 正向** 取第一个命中（正向兜底）
- 步骤可执行性判据：步骤含具体入口、输入值、操作对象；不含"等一下""适当输入"
- 预期可判定判据：预期结果有具体值/文案/状态，可直接判 pass/fail
- 前置条件与测试数据分离：前置是状态，数据是输入

## 输入与历史测试用例使用规则（S7）

S7 输入以派发单和 S6 资料质检报告为准：**必须** = S5 验收通过的 `output/test-point/test-point.md` 基线 + 测试点生成资料包（当前 PRD/功能目录 `prd.txt`、会话目录 scope.md、S2 已登记且可用的领域知识、逆向文档、功能知识、存量测试点）+ 经 S6 适用性判定为必需的前端设计（`develop-docs/fe-design/`，判「不适用」者豁免）+ 后端设计（`develop-docs/be-design/`）；**可选** = 数据库设计（`develop-docs/db-design/`）、存量测试用例（`asset-library/test-case/`）。具体路径以经理派发单按工作空间目录契约列明为准。S7 产物写入功能目录 `output/test-case/test-case.md`。

可选资料不存在或为空时标注「未提供」并跳过；存在且可读时参考使用；存在但不可读时不得静默跳过，应移交经理处理。会话 `input/` 中的澄清附件只用于理解已登记的用户澄清，不属于默认生成资料；用户明确要求作为额外依据时，经理须在资料质检报告和派发单中登记。适用时必需的前端、后端设计任一缺失或不可读都应暂停 S7 并请经理处理。PRD 与已验收 TP 是需求和范围基线；设计材料不得推翻二者，冲突须交经理请用户澄清。

存量测试用例仅作场景与步骤写法参考：**禁止照抄历史编号与标题**——每条 TC 仍须满足十字段规范、关联本次验收基线的 TP；存量用例与 TP 基线、PRD 或本次设计材料冲突时，以 PRD、已验收 TP 和本次通过质检的设计材料为准。

## 变更规则

- S9 评审调整 → 修订对应行并重跑 S8 质检（经修复循环后重新评审）
- 设计材料变更或此前缺失的必需资料补齐 → 按 test-manager 材料变更协议复查受影响资料，受影响 TC 标记失效并重生成、重跑 S8 质检；未受影响的已确认基线保留
- 「变更状态」列保留为模板列序契约的一部分，当前流程（S7/S8/S9）一律留空，不承担变更分析功能
