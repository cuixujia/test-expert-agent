# PRD 质检方法——唯一定义源

## 锚点（证据）规则

锚点是 PRD 原文的定位标记，是「所有测试内容必须可回查需求原文」的证据链基础。

1. **编号与格式契约**：PRD 已有编号直接用——章节号（3.2.1）、需求号（REQ-001）、事件/规则/对象号（E01/B01/R01/O01）都算；**表格行自带序号的也视为原文编号**，格式为 `<章节号>-<行号>`（如 3.3-1、3.2-5）；都无编号才按 `M<模块>-S<章节>-P<段落>` 生成。**底册锚点必须符合三种格式之一（validate.sh scope 模式强制校验，建册即拦）**：
   - 章节号：`3.2`、`6.1.1`，可带一个数字后缀如 `3.2-1a`、`7.1-1`；无点号的章节+行号形式 `5-1` 也合法（纯数字必须带后缀或点号，避免与普通数字混淆）
   - 字母编码：字母开头且含数字，可带字母数字后缀，如 `E01`、`B02-1`、`R01-1`、`F01-Q1`
   - M-S-P：`M1-S2-P3`

   **禁止自创越界格式**（含中文后缀、纯中文、无数字纯字母串等，如 `6.1.1-完成标准1`、`F01-待澄清`、`表外复用`）——语义放条目摘要中表达，锚点本身改为合规形式（如 `6.1.1-1`、`F01-Q1`）
2. **锚点底册（scope.md，全流程唯一证据底册）**：确定目标功能后，通读 PRD，仅为该功能及必要横切依赖建锚；**建册后冻结**，唯一例外是完备性扫描发现的缺锚经用户确认后受控补录（登记补录版本）
3. **粒度**：一节含多条可独立判定的硬规则（不同流程/规则/结果）时，锚点细分到子句级（如 `4.3.4a/b/c`），摘录取对应子句原句——禁止一节多规则共用一个锚点（摘录与验证意图错位必然引发底册返工）；纯背景、元信息、目录类章节不建锚
4. **摘录**：≤40 字连续原句，禁止跨段拼接；必须逐字命中 PRD 文本快照（validate.sh 机验）。TP 引用锚点必须附摘录，防幻觉依据
5. **去重**：语义重复段落只保留更具体/更权威的一条，其余注明「由 <锚点> 覆盖」；有独有条件或结果的分别保留
6. **引用链轻登记**：目标功能引用其他功能处（如「编辑在 FUNC-04 定义」）逐项登记：锚点=被引功能编号，摘录=引用处原句；仅作检索入口，不展开全文
7. **功能码**：TP/TC 编号的功能码直接取平台 bizFunctionId（功能目录名），仅作编号用途，不替代名称；名称引用一律与 PRD 原文逐字一致，禁止缩写改写
8. **PRD 文本快照（prd.txt）**：建底册时把权威 PRD 转纯文本落功能目录（推荐 `bash validate.sh "<功能目录>" snapshot "<PRD 文件名>"`，内置引号归一；**禁止模型转写**）。快照只读、已存在即拒绝重建；归一后字符是全链路唯一基准。内嵌图片等不可解析内容**先自行解读**（标「AI 解读待确认」），无法解读才降级声明并交用户确认；PDF/图片等不可文本化材料在 scope.md 写 `> 快照机验：跳过（<原因>）` 降级
9. **PRD 版本锁定**：快照与底册建立时登记 PRD 原件 md5；此后 PRD 文件变化 → 暂停，用户二选一（恢复原 PRD / 按新 PRD 重开）；流程内不支持修改 PRD 文件，问题一律靠澄清登记

### scope.md 模板（validate.sh 校验契约）

```markdown
# <目标功能> 锚点底册
（仅当 PRD 不可文本化时保留下一行降级声明）
> 快照机验：跳过（<原因>）

## 锚点清单
| 锚点 | 条目摘要 | 原文摘录 |
|---|---|---|
```

## PRD 质检（以「足以定义测试点」为准，不追求可写全部 TC）

**目的**：确认需求文档足以支撑「有证据、范围清楚、结果可判定」的业务级 TP。不影响 TP 归组、拆分或判定的 TC 级细节（字段枚举、精确文案、错误码等）**不属于检查范围**：不登记、不上报，由后续环节按各自的检查单覆盖。

| 维度 | 必查：影响 TP 的内容 | 不查：TC 级细节 |
|---|---|---|
| 完整性 | 业务目标、功能范围、角色、关键前置、结果方向、主要分支、排除项与外部依赖 | 全量测试数据、字段取值枚举、详细边界值、页面文案布局 |
| 一致性 | 与关联流程/跨模块规则冲突；关键术语同义性 | 不影响行为的文字格式问题 |
| 无二义性 | 歧义改变目标归属、拆分或通过标准 | 展示实现细节 |
| 可测试性 | 每项能力有可观察结果方向；无不可确认的外部依赖 | 造数方案、字段组合、精确文案 |
| 可追溯性 | 每项 TP 可定位到原文；目标/排除范围可区分 | 无关的修订历史整理 |

### 矛盾检测（检索交给工具，判定交给 LLM）

先按种子词表用检索工具在 PRD 全文定位，再对命中条目做语义比对，结论留痕。种子维度（候选态，前两个必查）：数据可见范围（可见/权限/范围/创建人）、操作入口归属（按钮/入口/编辑/删除/只读）、状态流转、角色能力、字段与统计标准、时间与触发条件、校验时机。矩阵未捕获的矛盾不视为流程失败。

### 防误报两道闸

- **有意决策三问**（对「PRD 未给量化标准/细节」的候选）：①PRD 声明有意留白？②给了验证方式（哪怕主观走查）？③不影响 TP 归组/拆分/判定？三问全满足 → 不登记
- **登记前最后一问**：该问题会产生两种互斥预期结果，或改变 TP 的归组/拆分/通过判定？否 → 不登记。「输入不全」默认属 TC 级细节不登记，仅当该能力整体无任何判定依据才登记
- **待核验标记消歧**：PRD「待核验」只吸收该条目自身未定部分；已写死内容之间的冲突（任何结论下都存在的矛盾）必须登记

### 歧义处置

- 并列条件未说明是否区别处理 → 按 tp-spec 合并规则默认合并，歧义记入问题清单
- 通过标准无法确定 → 记待澄清，不得自行补造预期
- PRD 明确的字段约束/边界/枚举/异常，即使不增 TP 数量，也必须建锚进底册

### 完备性扫描（防底册漏锚）

五维质检后、出报告前执行：`bash "<路径>/validate.sh" "<会话目录>/scope.md" scan` 一次产出章节锚点覆盖状态与功能名命中行；**只对「疑似缺锚候选/无编号/部分覆盖」行做三判定**（已建锚/疑似缺锚/范围外）；疑似缺锚列待用户确认后补录底册。禁止逐词 grep 循环。

## 问题分级

只登记影响 TP 定义与判定的问题，两级：

- **Blocker**：目标业务能力或通过标准无法确定，无法生成可判定的 TP
- **Major**：可形成暂定 TP，但未决问题可能改变范围、拆分或验收结果

## 报告模板（prd-check.md）

```markdown
# <目标功能> PRD 质检报告

## 结论
Blocker: N 项 / Major: N 项
是否可进入生成阶段：<是 / 否，原因>

## 问题清单
| 问题编号 | 维度 | 锚点 | 问题描述（现状→差异→影响） | 级别 | 改进建议 |
|---|---|---|---|---|---|

## 资料清单
| 资料类型 | 路径 | 必需/可选 | 提供情况 | 可读性与相关性 | 使用限制 |
|---|---|---|---|---|---|

## 处置记录
| 日期 | 问题编号 | 用户处置 | 备注 |
|---|---|---|---|

## 附录：完备性扫描（只登记非「已建锚」行）
| 命中位置 | 判定 | 说明 |
|---|---|---|
```

**报告瘦身铁律**：不设候选判定留痕、挑战位等过程性附录；只写结论性发现，不逐条罗列「检查过且无问题」；复查轮次每条复核结论一行，禁止重贴摘录与行号。

## 澄清登记（CL）

用户澄清/补充的结论由流程编排者以 `CL-<序号>` 登记状态文件（编号唯一，validate.sh state 模式校验）；后续报告与派发只引用 `CL 编号 + 一句话关键结论`。用户澄清结论可作为 TP 依据，注明 CL 编号。
