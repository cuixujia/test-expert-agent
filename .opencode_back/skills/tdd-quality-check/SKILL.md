# 测试用例生成资料质检规范（S6 唯一权威源）

## 质检目的与深度

S6 的目的：确认已验收测试点及其依据可继续使用，且生成 TC 十字段所需的适用设计资料可用（适用性判定见下方输入资料范围表；字段规范见 test-case-spec）。同时以 scope.md 锚点底册核对 PRD 已明确约束的字段、边界、枚举和异常要求在设计材料中有对应覆盖方式。

- 检查深度 = 支撑 TC 生成，不要求实现级精度
- 材料未覆盖的：说明对 TC 生成的影响并登记缺口，不得静默丢弃，不得替材料补造约束
- 锚点底册的建册与引用规则见 prd-quality-check，本 skill 不复述

## S6 输入资料范围

| 资料 | 要求 | 质检规则 |
|---|---|---|
| S2 测试点生成资料包 | 继承复用 | 核对 PRD 版本/指纹、scope.md、S2 资料清单与澄清登记；只复查发生变化或影响 TC 的资料，不重复完整执行 S2 |
| 已验收测试点 | 必需 | 确认状态为已验收、编号和 PRD 锚点可追溯，且覆盖当前目标功能 |
| 前端设计 | 适用时必需 | 经理按 PRD/TP 类型先判适用性：功能含操作界面 → 必须有可读材料，检查页面入口、交互、校验、提示和适用的兼容性要求；纯接口/纯算法等无界面功能 → 登记「前端设计不适用」并继续 |
| 后端设计 | 必需 | 必须有可读材料；检查接口、状态、权限、异常、事务及适用的并发/幂等等约束 |
| 数据库设计 | 可选 | 有则检查字段、类型、长度、枚举、默认值和约束；无则登记「未提供」并继续 |
| 存量测试用例 | 可选 | 有则登记并供 S7 参考；不得复制历史编号，不得取代已验收 TP；无则登记「未提供」并继续 |

- 前端、后端设计中经适用性判定为必需的项是硬门槛：任一缺失、不可读，或存在影响用例步骤、测试数据、预期结果的未解决问题，S6 结论为「暂不可进入 S7」，测试经理须请用户澄清或补充。经理判定功能无界面时登记「前端设计不适用」继续（登记进 design-check.md 材料清单）；判定存疑（如 PRD 是否含界面描述不清）时请用户确认，登记结论后继续。质检复核适用性判定：PRD 明示界面要求却被判不适用时列为问题。
- 可选资料不存在或为空时标注「未提供」并继续；可选资料存在但不可读时不得静默跳过，须列明影响并请用户处理或明确同意跳过。
- 对已提供材料先检查目录、全局规则，再围绕已验收 TP 深读相关章节及交叉引用。报告记录实际检查范围；未变化的 S2 资料复用既有结论，避免重复精读。
- S6 无待用户处理问题时报告「可进入 S7」，自动推进，不额外要求用户确认。

## 五维检查（检查深度 = 支撑 TC 生成）

| 维度 | 必查：影响 TC 生成的内容 |
|---|---|
| 完整性 | TC 十字段所需细节：操作入口、字段约束、枚举、错误码、状态定义、异常路径能否从材料获得 |
| 一致性 | 设计材料与 PRD 锚点底册约束的匹配；前端与后端设计文档之间接口契约一致 |
| 无二义性 | 歧义是否会改变 TC 的操作步骤、测试数据或预期结果 |
| 可测试性 | 预期结果可观察、可判定；测试数据可构造 |
| 可追溯性 | 每条设计约束能定位到具体文档与位置 |

## 材料专项检查项

| 材料类型 | 检查项 |
|---|---|
| 前端设计文档 | 页面元素与操作入口、交互事件、提示文案、前端校验规则、兼容性说明 |
| 后端设计文档 | 接口契约、状态机定义、并发与锁、事务边界、批处理时序、错误码表、幂等约定 |
| 数据库设计（可选） | 字段类型/长度/枚举值、默认值、主外键与级联约束 |
| 存量测试用例（可选） | 场景与步骤参考；不得复制编号或将历史用例当作本次验收依据 |
| 接口文档 | 请求/响应字段约束、错误码表、幂等约定、签名加密规则 |
| 流程图/时序图 | 分支完整性、异常路径、超时处理（不可解析时触发降级声明，规则同 prd-quality-check 报告降级） |

- 必需资料问题：适用性判定为必需的任一设计缺失/不可读，或 TP 基线未验收，必须暂停 S7 并请用户澄清/补充。不得将缺失的必需设计当作可选资料，也不得自动豁免受影响 TP。用户明确要求带风险推进时，只能走 test-manager 的 Blocker 二次确认规则并登记风险；报告须说明风险和影响。
- 可选资料：数据库设计、存量测试用例缺失或为空时登记「未提供」并继续，不补造材料中不存在的约束；可选资料存在但不可读或与 PRD/TP 冲突时列为问题，不得静默忽略。
- 超长文档必须分页读完，禁止只读首屏下结论

## 问题分级

沿用两级分级，判定基准为 TC 可生成性（分级定义见 prd-quality-check）：

- **Blocker**：受影响 TP 的 TC 无法生成或预期无法判定
- **Major**：可暂定 TC，但缺口可能改变 TC 的步骤、测试数据或预期结果

## 资料问题处置与阶段衔接

- 资料问题、用户澄清和复查结果记录在 design-check.md；测试经理在 state.md 登记 CL 编号和必要的风险决策。
- 必需资料问题解决后，质检专家只复查受影响资料；通过后自动进入 S7。
- 可选资料未提供不阻塞 S7；S7 仍须覆盖每条已验收 TP，除非经过现有风险推进规则明确批准并记录。
- 前端、后端或数据库设计后续变更时，按 test-manager 材料变更协议只复查受影响 TP/TC。

资料路径按 `DESIGN/工作空间目录结构.md`：前端/后端设计通常位于功能目录 `develop-docs/fe-design/`、`be-design/`（必需），数据库设计 `develop-docs/db-design/`（可选），存量测试用例 `asset-library/test-case/`（可选）；实际以经理派发单列明路径为准，质检报告的材料清单须写明每项的实际路径。

## 处置协议

1. 用户补充材料后：复查受影响问题，更新处置记录与结论；受影响产物按材料变更协议处理
2. Blocker 未清零：声明风险 → 用户以「通过 + 阶段名」二次确认 → state.md 登记降级决策

## 报告模板（design-check.md）

```markdown
# <目标功能> 测试用例生成资料质检报告

## 结论
Blocker: N 项 / Major: N 项
是否可进入 S7：<是 / 否，原因>

## 材料清单
| 材料类型 | 路径/文件名 | 版本/指纹（可取得时） | 必需/可选 | 提供情况 | 可读性与相关性 | 检查范围/结论 |
|---|---|---|---|---|---|---|

## 问题清单
| 问题编号 | 维度 | 材料来源 | 问题描述 | 级别 | 改进建议 | 对测试的影响 |
|---|---|---|---|---|---|---|

## 处置记录
| 日期 | 问题编号 | 用户处置（已补充/澄清/接受现状/拒绝） | 备注 |
|---|---|---|---|

## 附录：候选判定留痕
| 候选 | 处置（登记/不登记） | 一行理由 |
|---|---|---|

> 挑战位：若您发现本报告未列出的疑似缺失或矛盾，请直接提出，我将按判据核实后补充登记或说明不登记理由。
```

**问题清单措辞要求**：遵循表达四原则，「问题描述」「对测试的影响」两列按「现状（哪里写了什么）→ 差异/缺失 → 影响」直白句式，一句话说清。
